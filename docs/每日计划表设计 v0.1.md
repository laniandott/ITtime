## 一、背景与定位

### 1.1 要解决的问题

用户需要一个"每天每小时做什么"的计划表。动机是：没有明确时间的计划会懈怠，有明确时间的计划会自觉执行。

### 1.2 为什么不能做成"记事本模板"

记事本的按时计划模板是**静态**的：早上填一遍，晚上不会回看。它只能回答"我打算做什么"。

ITtime 手里有另一半牌——**真实发生了什么**。所以本功能的价值不在模板本身，而在**计划与实际的对照**：

- 计划编程 3h，实际 2.5h，偏移 40 分钟
- 计划外时间 2.2h（这段时间没在任何计划块里）
- 按时开始率 62%

这是静态模板永远给不了的。**本功能的设计目标不是"更好的计划表"，而是"计划—执行—复盘"的闭环。**

### 1.3 为什么是独立实体，不能塞进 Todo / Calendar

| 概念 | 语义 | 现状 |
|---|---|---|
| Todo | 要做的事，**没有时间槽** | 已有 |
| **PlanBlock** | 打算**何时**做，有明确时间槽 | **本功能新增** |
| TimeEntry | **实际**发生的事 | 已有 |

三条硬性隔离理由：

1. **不能塞进 Todo**。Todo 是"无时间槽的意图"。混入计划会让待办列表退化成时间表，并直接违反 v0.4 不变规则 1「停止计时不自动完成 Todo」——计划到期 ≠ 待办完成。
2. **不能塞进 Calendar 的现有视图**。日历是**回看**视图（已发生活动色点 + 外部 ICS 订阅）。混入计划会让同一网格同时承载"已发生"和"打算发生"两种语义。
3. **不能进入时长统计**。违反 v0.4 不变规则 6「删除、同步和恢复不能让统计悄悄改变语义」。"今日时长"必须是可信的实际值，一旦掺入计划值即失去意义。

### 1.4 本功能明确不做的事

- 自动排程、智能建议、AI 复盘（v0.4 暂缓事项）
- 计划块自动完成 Todo / 自动改写 TimeEntry 状态
- 跨午夜计划（MVP 阶段不支持）
- 重复计划规则（MVP 只做单日；"计划模板"留待后续）
- 主动提醒通知（Android 通知基建已具备，列为 v1.1）
- 精力 / 心情 / 地点等状态维度（v0.4 暂缓事项）

## 二、数据模型

### 2.1 新增实体 PlanBlock

**存储位置：浏览器本地 PouchDB，不建服务端表。**
理由：计划是纯新增数据，无历史存量需要迁移；`MIGRATION_STATUS.md` 已确立"核心实体本地优先、服务端 SQLite 只保留日历/笔记/上传"的方向。建服务端表等于维护第二套实现，无收益。

文档 ID 格式沿用现有约定：`plans:<id>`。

```ts
// apps/web/src/types.ts
export type PlanDisposition = 'planned' | 'skipped' | 'deferred'
export type PlanExecutionStatus = 'upcoming' | 'active' | 'paused' | 'done' | 'partial' | 'missed'

export interface PlanBlock {
  id: string
  date: string            // 'YYYY-MM-DD'，本地日历日。刻意用"日 + 分钟"而非 ISO 时间戳
  startMinute: number     // 0..1439，从当日 00:00 起的分钟数
  endMinute: number       // (startMinute, 1440]，不允许跨午夜
  content: string         // 必填，多行自由文本：用户自己填写的"具体要做什么"
  tagId: string | null    // 可选挂载。用于分类和无 planId 计时时的自动对照
  todoId: string | null   // 可选关联待办
  skippedAt: string | null      // 用户显式"这段不做了"的时间戳
  confirmedAt: string | null    // 用户手动确认"这段我做完了"的时间戳
  deferredFromId: string | null // 新计划块指向原计划块；原块是否被推迟由反向查询派生
  createdAt: string
  updatedAt: string
}
```

**内容为主，标签可选。** 计划块的首要内容是用户自己填写的多行文本，用来写清楚"具体要做什么"；标签不是计划的身份，而是一个可选挂载。挂上标签的收益是**让计划与实际计时能自动对照**（见 §2.4），不挂标签则只能靠用户从该块点"开始"或手动确认。

`content` 是必填字段：trim 后不能为空，上限 2000 字符。格子里显示其前两行，超出部分截断，点开抽屉看全文。不再单独设 `title` 和 `note`——多行文本本身已经承载了这两者的作用。

v0.1 不直接保存 `goalId`。计划与 Todo、Goal 只保留关联展示关系，不参与目标进度计算；目标进度只从实际 `TimeEntry` 按标签统计。若 Todo 本身关联了 Goal，计划详情可以展示这条间接关系，但不得把它当作计划的目标贡献。

**为什么用 `date + startMinute/endMinute` 而不是 ISO 时间戳：**

- 计划是"墙上时钟"语义。9:00 的计划就是当地 9:00，不应因时区换算、夏令时、跨时区旅行而漂移到别的日子。
- 范围查询极简：今日 = `date === today`；本周 = `date` 落在 7 天内。
- 与用户心智一致（记事本模板就是"日期 + 时间段"）。
- 避免了 `TimeEntry` 那种 ISO 时间戳在跨时区设备上"计划跳到前一天"的经典 bug。

### 2.2 TimeEntry 扩展

```ts
// apps/web/src/types.ts —— TimeEntry 增加一个可选字段
planId?: string | null
```

这是整个功能的关键缝合点：从计划块一键开始计时，实际记录回指计划块，从而支持追溯。`planId` 不是对照计算的唯一依据，因为一次实际计时可能跨越多个计划块。

#### 续接链规则

- 由 `resumedFromId` 续接的记录继承原记录的 `planId` 和 `todoId`；这是执行来源追溯，不取代时间窗口重叠算法。
- 由 `interruptedFromId` 接管的记录不继承原记录的 `planId`。接管代表开始一个新的活动段，即使用户选择了同一个标签，也不能把它自动算入原计划。
- 本地路径和服务端路径都必须校验 `resumedFromId` 的标签一致、待续状态，以及 `interruptedFromId` 的待续状态，避免两条路径产生不同语义。
- 终止链路只改变已有记录的结束、放弃和原因字段，不删除计划关联。

服务端 `schema.prisma` 的 `TimeEntry` **不加此字段**——`/timer/start` 路径由 `isLocalPath` 判定为本地，永远不走服务端。

### 2.3 状态派生规则（不存储）

计划不保存一个混合语义的 `status`。返回给界面的是三个**互不合成**的信号：`disposition`（用户意图）、`executionStatus`（客观计时覆盖）、`confirmed`（用户手动确认）。分别派生或存储，避免把“用户决定不做”“实际计时了多少”“用户认为做完了”塞进同一个可写字段。

`disposition` 的判定顺序：

| 条件 | `disposition` |
|---|---|
| `skippedAt` 非空 | `skipped`，优先级最高 |
| 存在一个或多个 `deferredFromId === this.id` 的后继块 | `deferred` |
| 其他情况 | `planned` |

`executionStatus` 独立判定。**它只描述计时覆盖，不描述用户是否认为自己做完了：**

| 条件 | `executionStatus` |
|---|---|
| 有未结束的关联 entry | `active` |
| 有 `pendingResume` 的关联 entry，且没有未结束 entry | `paused` |
| 有已结束关联 entry，覆盖率 ≥ 0.9 | `done` |
| 有已结束关联 entry，覆盖率 0.3 ~ 0.9 | `partial` |
| 有已结束关联 entry，覆盖率 < 0.3 | `missed` |
| 无关联 entry 且窗口已过 | `missed` |
| 无关联 entry 且窗口未到 | `upcoming` |

覆盖率 = 关联 entry 与计划窗口的**重叠分钟数** / 计划分钟数（`endMinute - startMinute`）。

`confirmedAt` 是第三个独立信号，不参与上面的判定：用户手动勾选"这段我做完了"时写入，取消时清空。

三个信号的职责：

| 信号 | 来源 | 含义 |
|---|---|---|
| `disposition` | 用户意图（存储） | 我打算做吗：`planned` / `skipped` / `deferred` |
| `executionStatus` | 计时记录（派生） | 客观计时覆盖到什么程度 |
| `confirmed` | 用户确认（存储） | 我主观确认做了吗 |

**三者不合成单一达成率。** 一个未挂标签、用户手动勾完成的计划，`executionStatus` 仍是 `missed`（客观上确实没有任何计时记录），同时 `confirmed === true`。界面必须把两者分开呈现；`missed` 的文案要写成"无计时记录"而不是"未执行"，否则会和"已确认完成"自相矛盾。

“推迟”不是把原块直接改到新时间，而是保留原计划块并只新建一个带 `deferredFromId` 的后继计划块。原块的 `deferred` 意图由反向查询派生，避免跨文档双向指针和悬空引用。MVP 中后继块一旦创建不可直接删除，只能标记跳过，以保留推迟历史；若未来允许删除，必须连同可解释的历史标记一起设计。两台设备同时推迟同一原块时，服务层按原块和目标时间生成幂等键，重复请求返回同一个后继块。

### 2.4 计划与实际的对照算法

对照不能只查询 `TimeEntry.planId === plan.id`。一个 9:00–11:00 的实际计时可能跨越 9:00–10:00 和 10:00–11:00 两个计划块，只依赖外键会把第二块误判为未执行。

算法规则：

1. 把本地、未放弃的 TimeEntry 转为当天的分钟区间；未结束记录按查询时刻裁剪。
2. 对每个计划块，优先纳入显式 `planId` 相同的记录；没有 `planId` 的记录，仅在 `tagId` 精确相同且时间窗口重叠时作为候选。MVP 不把一级标签和二级标签自动视为相同标签。
3. 计划块的实际覆盖时长使用候选交集的**区间并集**，避免同一段实际时间因多个记录重复计算。
4. `plannedMs`、总体 `actualMs` 和 `unplannedMs` 统一先取区间并集，再计算比例；同一段时间不能因计划块重叠或计时记录重叠而重复计入。
5. MVP 在单设备创建和编辑时拒绝同一天的计划块互相重叠。CouchDB 离线同步可能引入重叠，因此这不是跨设备的绝对不变量；同步后必须保留两块、正常显示，并在计划卡片上标记“与其他计划重叠”。单块覆盖率各自按候选交集并集计算，总体时长指标按全体窗口并集计算。未来若开放重叠计划，必须另行定义不重复分配规则。
6. 手动确认（`confirmedAt`）不参与任何时长计算。`plannedMs`、`actualMs`、`unplannedMs` 和覆盖率都只看计划窗口与实际计时，与用户勾选无关。

**未挂标签计划的特例**：`tagId === null` 的计划块没有标签兜底，只能通过显式 `planId` 关联实际记录。它要么由用户从该块点"开始"（补选标签后计时），要么只能靠手动确认——不会因为"标签相同"被自动匹配。这是"内容为主、标签可选"之后的必然结果，界面需要对这类计划明确提示"未挂标签，无法自动对照"。

标签选择器只列出可以直接启动计时的时间型标签。MVP 使用精确 `tagId` 匹配，不自动把一级标签和二级标签视为相同；因此用户把计划挂到一级标签、却把实际计时记在二级标签时，系统不会自动对照，界面需要在选择时提示这一限制。

因此，`planId` 是执行来源和追溯字段，时间窗口重叠才是计划与实际对照的兜底规则。

### 3.5 `apps/web/src/localStats.ts`

新增纯函数，可独立单测：

```ts
export interface PlanAdherence {
  // 客观口径：只由计划窗口与实际计时决定
  plannedMs: number        // 计划总时长（按窗口并集）
  actualMs: number         // 计划块覆盖的实际时长（按区间并集）
  unplannedMs: number      // 总实际时长 − 计划覆盖的实际时长（"计划外时间"）
  coverageRate: number     // actualMs / plannedMs
  onTimeRate: number       // 按时开始率：|开始偏移| ≤ 阈值 的块占比
  missedCount: number      // 无计时覆盖且 disposition 不是 deferred/skipped 的块数
  // 主观口径：用户手动确认，与上面互不合成
  confirmedCount: number
  confirmedRate: number    // confirmedCount / 计划块总数
  // 意图口径
  skippedCount: number
  deferredCount: number    // 主动推迟的原计划块数，不计入 missedCount
}
export function planAdherence(blocks: PlanBlock[], entries: TimeEntry[], range: [number, number]): PlanAdherence
```

**关键约束**：`planAdherence` 只读取 plans 和 timer，**不得被现有的 `elapsed()` / `StatsPage` 实际时长统计引用**。两组指标完全隔离。目标进度也不从计划块计算，只从实际 TimeEntry 的标签计算。

**客观与主观必须分开呈现。** `coverageRate` / `missedCount` 来自计时记录，`confirmedRate` 来自用户勾选，两者**不得合成单一达成率**（见 §2.3）。理由：未挂标签的计划没有计时兜底，一旦合成，手动勾选就会直接抬高客观覆盖率，指标随即失去意义。

## 四、界面设计

### 4.1 导航决策：不新增底部 tab

底部导航已有 6 项（打卡 / 待办 / 习惯 / 统计 / 日历 / 设置），加第 7 项会挤压移动端触控区。

采用**双层设计**：

| 层 | 位置 | 用途 | 频次 |
|---|---|---|---|
| **每日计划工作区** | 独立 `/plans` 页面与主导航 | 按日查看全天分钟时间轴、填写和调整计划笔记 | 每天多次 |
| **周计划视图** | `CalendarPage` 现有周 / 4 天视图中的计划图层 | 提前排程、拖动调整 | 每周几次 |
| **计划指标** | `StatsPage` 新增"计划"tab | 计时覆盖、手动确认、计划外时间（三者不合成） | 每周复盘 |

计划以独立页面作为主工作区，避免被计时操作挤压。计划块内仍可发起计时；Calendar 保留计划图层用于跨功能查看，Stats 单独展示计划与实际差异。

### 4.2 分钟级时间轴（日视图）

分钟级粒度在小屏上的核心矛盾是**总高度**。方案：

- 每小时固定 **60px**，全天 **1440px**，容器纵向滚动。即 **1 分钟 = 1px**。
- 刻度层级：整点 = 实线 + 时间标签；15 分 = 短虚线；5 分 = 更浅的点。
- 拖拽吸附 **5 分钟**（5px），兼顾灵活与好点选。
- 计划块内显示 `content` 的**前两行**（按换行切分），超出部分截断加省略号；点开抽屉看全文。
- 块高 < 15px（即短于 15 分钟）时只渲染色条，文本走 tooltip。
- 30 分钟块 = 30px，够显示一行；60 分钟块 = 60px，够显示两行。
- 挂载了标签的块在左侧显示标签色条，未挂标签的块用中性灰——让"能否自动对照"在视觉上一眼可辨。

### 4.3 周计划视图

复用 `CalendarPage` 现有周 / 4 天视图，不新增“计划”视图类型。计划块作为内部图层加入日视图和 4 天 / 周视图；月视图继续遵守 v0.4 规则，只显示色点，点击日期后在详情区域查看计划内容。

### 4.4 计划块编辑

点块 → 底部抽屉（Sheet）：

- **主输入是内容**：一个多行文本框，占据抽屉的主要面积，光标默认落在这里。用户先写"具体要做什么"，其余都是可选项。
- 开始 / 结束时间用"时:分"数字选择器，**精确到分钟**。可复用 `components/DateTimeSecondPicker.tsx` 的交互模式。
- 标签是**可选挂载**：默认未选，复用现有分类分组的有序选择器。未选时给出提示"未挂标签，无法与实际计时自动对照"。
- 可选：关联待办。
- 操作：保存 / 删除 / 这段不做了（skip）/ 标记完成（confirm）。

**创建流程同样是"先写内容"**：点时间轴空格子 → 直接在格内输入文字 → 回车创建（默认 30 分钟时长）→ 需要时再挂标签。**不是先选标签再拖进格子。**

**校验**：`content` 为空时保存按钮置灰；超过 2000 字符时截断并提示。

### 4.5 计划 vs 实际对照

日视图内，计划块与真实计时条**并排双列**：

```
时间轴        计划（用户填写）          实际计时
09:00 ┤  ┌──────────────────┐   ┌────────┐
      │  │ 写季度报告初稿    │   │ 编程   │
12:00 ┤  └──────────────────┘   └────────┘
      │  ┌──────────────────┐        ↑ 实际晚 40 分钟开始
13:00 ┤  │ 午休 + 散步       │   ┌──────┐
14:00 ┤  └──────────────────┘   └──────┘
      │    ↑ 无计时记录（灰斜纹）· 另有"已确认"勾选
```

无计时覆盖的计划块用灰色斜纹填充——注意这表示"**没有计时记录**"，不等于"没做"；偏移超过阈值时在实际条上标出偏差。手动确认的状态用独立的勾选标识呈现，不改变斜纹，避免把主观确认混进客观视图。

### 4.6 组件拆分（重要）

计划本身是一个独立页面，时间轴和笔记编辑器放在独立文件；Calendar、Timer 和 Stats 只接入各自需要的轻量关联入口：

```
apps/web/src/pages/PlansPage.tsx         独立每日计划笔记与分钟时间轴
apps/web/src/pages/CalendarPage.tsx      Calendar 中的计划图层与跨日期入口
apps/web/src/pages/StatsPage.tsx         独立的计划遵循度指标
```

## 五、关键交互流程

### 5.1 一键开始

计划块上**始终**提供"开始"。但 `TimeEntry.tagId` 在 `schema.prisma` 里是**必填**字段，没有标签就产生不了实际记录，所以未挂标签的块需要先补选标签：

```
用户点计划块"开始"
  ├─ 已挂标签 → 直接开始
  └─ 未挂标签 → 弹出标签选择器，选完立即开始，并把选中的标签写回计划块
  → store.start({ tagId, note: undefined, todoId: block.todoId, planId: block.id })
  → localData POST /timer/start（body 带 planId）
  → 写入 TimeEntry.planId = block.id
  → 计划块派生 executionStatus 变为 active
```

**参数形式必须注意**：现有 `start` 是位置参数 `(tagId, note?, todoId?, interruptedFromId?)`（`store.ts:17`），第 4 位是 `interruptedFromId`。`planId` **不能**填在第 4 位——否则会把计划块 id 写成"接管源"：本地路径目前不校验该字段，会静默写入坏数据；按 §2.2 补上校验后会直接抛错。本设计统一改为对象参数（见 §3.4）。

补选标签时把标签**写回计划块**，是为了让这个块从此进入自动对照范围，否则用户每次都要重选。写回是一个独立的 `PUT /plans/:id`，不参与计时事务。

### 5.2 计划外时间

不在任何计划块窗口内的实际计时，直接计入 `unplannedMs`。这是本功能最有信息量的指标——它回答"计划之外我把时间花哪了"。

计划块执行中的暂停必须沿用现有待续栈：

- 计划关联的 TimeEntry 停止并设置 `pendingResume` 后，计划块显示 `executionStatus=paused`，并在计划详情中显示待续提示。
- 从待续记录继续同一活动时，新的 TimeEntry 继承 `planId`；原记录的 `pendingResume` 被消费。
- 从“选择接下来做什么”启动另一个活动时，新的 TimeEntry 只保留 `interruptedFromId`，不继承原计划。
- 用户选择“算了”或终止链路后，计划不再保持 paused，按已经发生的时间重新派生 `done`、`partial` 或 `missed`；不会自动跳过计划。

### 5.3 冲突与防抖

计划块会被频繁拖拽调整，容易产生大量中间 revision。对策：

- UI 层**乐观更新**（本地立即改，不等写库返回）。
- 拖拽**结束**才落库，提交前 **200ms 防抖**。
- 删除沿用现有 `deletedAt` 软删 + tombstone 复制机制。

### 5.4 手动确认完成

未挂标签的计划没有计时兜底，必须提供手动确认：

- 计划块卡片上提供勾选（`confirm` / `unconfirm`），写入或清空 `confirmedAt`。
- 勾选**不产生** `TimeEntry`，也不改变 `plannedMs` / `actualMs` / `unplannedMs` / 覆盖率。
- 界面把"计时覆盖"和"手动确认"分成两个独立标识（例如 `计时 45/60 分钟` 与 `已确认`），**不合成单一分数**。
- 挂了标签、且已有部分计时覆盖的块同样可以勾确认——例如计时只覆盖了一半，但用户认为事情已经做完。

## 七、文档同步：v0.4 需要补的内容

本功能会触碰 v0.4 的产品边界，必须同步更新，否则产生"哲学漂移"：

**1. 「二、核心概念和不变规则」表格增加一行：**

| 对象 | 作用 |
|---|---|
| 计划块 | 预期发生的事件。与实际记录分表存储，不参与时长统计 |

**2. 不变规则增加第 8 条：**

> 8. 计划块只描述预期，不参与时长统计，不自动改变 Todo 或 TimeEntry 的状态。删除、跳过和同步不能让"实际时长"口径发生变化。

**3. 阶段排期建议：**

本功能的设计可以现在完成。实现顺序建议遵守 v0.4 的依赖：先完成阶段一的待续栈和活动链验收，再在阶段二的数据与同步基础上接入本地计划实体；计划与实际的独立指标归入阶段三的可解释洞察。这样安排是为了复用已经验收的续接、同步和统计边界，不是把计划需求永久推迟；如果用户优先需要每日计划，可以先实现不依赖阶段三的内容输入、时间轴和本地 CRUD，再延后对照统计。

## 八、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 分钟级网格在手机上过密，难点选 | 高 | 1 分钟 = 1px + 5 分钟吸附；短块只显示色条；长按进精确编辑 |
| `TimerPage.tsx` 进一步膨胀 | 中 | 全部新代码独立组件，页面只加一个挂载点 |
| 计划污染时长统计 | 高 | `localStats.elapsed()` 不接触 plans；计划指标独立函数、独立 tab |
| 接管活动错误继承计划 | 高 | 只有 `resumedFromId` 继承 `planId`；`interruptedFromId` 永不继承，并加入反例测试 |
| 推迟产生悬空或重复后继块 | 高 | 只保存 `deferredFromId`；创建后继时做同日重叠校验和幂等约束 |
| 重叠计划导致单块达成率无归属 | 高 | 单设备写入时拒绝；同步引入时保留并标注重叠，各自覆盖率独立计算 |
| Goal 与计划标签冲突 | 中 | 计划不参与目标贡献计算，Goal 只按实际 TimeEntry 标签统计 |
| 本地与服务端计时校验不一致 | 中 | 为 resumedFromId / interruptedFromId 补本地校验，并加入 parity 测试 |
| 拖拽产生大量 revision | 中 | 乐观 UI + 200ms 防抖 + 拖拽结束才落库 |
| 与 v0.4 "原始记录工具"定位冲突 | 中 | 在 v0.4 显式写入边界规则（见第七节） |
| 计划块数量增长导致 `list('timer')` 全表扫描变慢 | 低 | 与现有 memos join 同构，量级可控；后续可加 `planId` 索引 |

## 九、验收标准

**数据层**
- [ ] 计划块 CRUD 走本地 PouchDB，刷新页面后仍在
- [ ] 计划块经 CouchDB 在两台设备间同步；设置页文档计数包含计划块
- [ ] 同一计划块在两台设备并发修改，字段级合并后两端一致

**核心闭环**
- [ ] 从计划块"开始"能创建计时记录，且 `planId` 正确写回
- [ ] 计划块的 `disposition` 与 `executionStatus` 分离派生，优先级明确
- [ ] 计划块执行状态按覆盖率正确派生为 done / partial / missed
- [ ] "这段不做了" 后 disposition 为 skipped，且不计入 missed
- [ ] 推迟只创建一个带 `deferredFromId` 的后继块，重复请求不会创建重复块
- [ ] 未挂标签的计划块点"开始"会先弹标签选择器，选完立即开始并把标签写回计划块
- [ ] 从计划块开始时 `TimeEntry.interruptedFromId` 必须为 `null`
- [ ] `resumedFromId` 续接继承 `planId`，`interruptedFromId` 接管不继承 `planId`
- [ ] 接管和续接的本地校验与服务端语义一致
- [ ] 计划块同日重叠创建和编辑会被拒绝
- [ ] 两台设备离线创建重叠计划并同步后，计划不丢失、不报错，卡片标注重叠且各自覆盖率可解释
- [ ] 跨两个相邻计划块的实际计时能按窗口重叠分别覆盖两个块
- [ ] `plannedMs`、`actualMs`、`unplannedMs` 都按区间并集计算
- [ ] pendingResume 期间显示 paused，结束待续或终止后重新派生执行状态
- [ ] 两台设备同时推迟同一计划块时，同步后只保留一个幂等后继块
- [ ] `content` 为空无法创建或保存；超过 2000 字符被拒绝
- [ ] 未挂标签的计划块不会因为"标签相同"被自动匹配到实际记录
- [ ] 手动确认写入 `confirmedAt`，且不产生任何 `TimeEntry`
- [ ] 手动确认后 `plannedMs` / `actualMs` / `unplannedMs` / 覆盖率均不变
- [ ] 界面把"计时覆盖"与"手动确认"分开呈现，不出现合成达成率

**统计隔离（最重要）**
- [ ] 新增计划块后，"今日时长"数字**不变**
- [ ] 计划指标与现有统计口径互不影响
- [ ] `unplannedMs` 在只有计划、无实际记录时为 0

**界面**
- [ ] 手机屏幕上计划条不溢出、主要按钮可见
- [ ] 拖拽吸附到 5 分钟，拖拽过程不产生中间 revision
- [ ] 计划/实际双列在日视图正确对齐
