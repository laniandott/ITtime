# ITtime 交互流程规范

> Phase 2 · 体验设计
> 配套文档：`IA_REVIEW.md` / `A11Y_RESPONSE.md` / `EMPTY_LOADING_ERROR.md`
> 依据代码：见 `IA_REVIEW.md` §0

**每条规范的格式**：触发 → 反馈 → 动效（时长） → 无障碍处理
**动效总则**：缓动统一 `--ui-ease: cubic-bezier(.2,.8,.2,1)`（已在 index.css 定义）。
- 微反馈（hover/press/颜色）：120–180ms
- 面板/弹层进出：200–260ms
- 布局重排（列表增删、卡片展开）：240–320ms
- 页面级切换：280–320ms（现有 `animate-page-in` 0.3s ✓）
- 禁止：>450ms 的任何过渡；禁止循环动画（除计时环与骨架屏）

## 1. 工作台 / 计时（TimerPage）

### 1.1 快速开始：标签按钮点击

**现状**（TimerPage.tsx 51–69, 200–213）
按钮带 `aria-pressed={isRunning}`，点击后走 `handleStart`：若该标签已在跑 → 停止；否则 → 启动 / 计数打卡。成功时设置 `feedback` 文案（页面顶部 `role="status"` 绿条）。失败走 `alert()`。

**问题**：
1. `feedback` 绿条渲染在 `<PageHeader>` **之上**（第 309 行，PageHeader 在 310 行）。计时开始后，用户的视线焦点在右栏的标签按钮上，而反馈出现在页面最顶部远端 —— 眼睛不会去看。
2. `alert()` 用于错误（209/238/251/263 行）——阻塞式模态，打断心流，且不提供"重试"动作。
3. 多个标签并行计时时，只有一条共享的 `feedback`，无法知道是哪个标签的操作结果。

**规范**

| 步骤 | 规范 |
|---|---|
| 触发 | 点击标签按钮（未在计时） |
| 反馈 | **就地反馈**：按钮自身进入 `aria-pressed=true` + `ring-2 ring-brand` + 图标区显示 1.2s 的对勾；同时**该标签在「活动时间线」顶部插入一条"进行中"条目**（当前时间线已有此数据，只需保证新条目可见）。全局 toast 用于跨页感知，位置固定在移动端底栏上方 / 桌面右下角 |
| 动效 | 按钮态150ms（scale .98 → 1，--ui-ease）；对勾 180ms 淡入→淡出；新条目插入 240ms `height + opacity` |
| a11y | 按钮文案随状态变化：`aria-label` = `开始计时：编码实现` / `正在计时：编码实现，点击停止`；toast 容器 `role="status" aria-live="polite"`；**禁止用 `alert()`**，改为 toast + 内联重试按钮 |

**触发：点击已在计时的标签（停止）**

| 步骤 | 规范 |
|---|---|
| 反馈 | 停止是**不可逆的**（会产生一条记录），需二次确认。但不要用 `window.confirm`——用一次性 inline 确认：按钮下方展开"停止并保存？[停止] [取消]"，2 项按钮，`取消` 默认聚焦 |
| 动效 | 确认条展开 200ms（`--ui-ease`），无位移抖动 |
| a11y | 确认条 `role="alertdialog"` + `aria-label`；打开时焦点移到「停止」，`Esc` 取消并把焦点还给原按钮；焦点陷阱在确认条内 |

> **理由**：停止计时是本应用最高频且**唯一产生持久数据**的动作，值得一次轻量确认；但模态 `confirm()` 在移动端 WebView 里体验割裂，inline 确认更轻。

**触发：计数型标签（`trackType === 'count'`）点击**

| 步骤 | 规范 |
|---|---|
| 反馈 | 计数按钮上直接显示 `今日 3` 的迷你计数徽标，点击后数字 1.2s 内翻倍动画（`key` 变化 + scale 1→1.15→1）；顶部时间线插入"点记录"条目 |
| 动效 | 数字翻倍 240ms；徽标出现 180ms |
| a11y | 徽标必须同时有 `aria-label="今日已打卡 3 次"`，不能只有数字；读屏用户点击后需听到播报 |

### 1.2 正在计时卡片的状态锚定

**现状**（TimerPage.tsx 356–412）
`running.length > 0` 时左栏显示计时卡片，右栏「快速开始」sticky；`running.length === 0` 时左栏 `hidden`，整个工作区变成单栏 + 快速开始 3 列（446行）。

**问题**：
- `running.length === 0` → `> 0` 时，布局从"单栏3列"变成"双栏（左计时 + 右 1 列快速开始）"。**正在计时的标签从 3 列网格中被挤到 1 列**，位置完全变化。用户的肌肉记忆失效。
- 多条并行计时时（`running.length >= 2`）网格变 `sm:grid-cols-2`，卡片尺寸跳变。
- 计时中的标签在快速开始里只有 `aria-pressed` + 一个 ring（CSS `.dark .timer-tag[aria-pressed="true"]`），**在亮色下没有 glow 兜底**（index.css 717–720 行只有 `.dark` 规则）。

**规范**

| 项 | 规范 |
|---|---|
| 视觉锚定 | 计时中的标签：1) 左侧 3px `border-l-brand` 实心条；2) 标签名加粗到 600；3) 图标区显示脉冲点（`@keyframes pulse-dot`，2s 循环，**prefers-reduced-motion 下改为静态实心点**）；4) 亮色和暗色使用同一套规则（不要只在 `.dark` 下加glow） |
| 布局稳定 | 快速开始的网格列数**恒定为 3 列**（`xl:grid-cols-3`），不因`running.length` 变化。空闲时用3 列（当前已是），运行中仍是 3 列但整体 `xl:grid-cols-[minmax(0,1fr)_minmax(300px,360px)]` 使快速开始收窄为右栏 —— **改法：右栏内部保持 `grid-cols-1`，运行/空闲仅改变外层列定义，且右栏宽度从 360px 提升到 400px 以容纳 2 列标签** |
| 空态 | 保留现有 `.timer-empty` 卡片（TimerPage 407–411），文案"点下面任意标签即可开始。正在计时的标签会清楚标出来。"—— 改为"点下方任意标签开始。**正在计时的标签会带青色左边条和脉冲点**"，把视觉规则写进空态，用户才知道要找什么 |
| a11y | 快速开始容器 `role="toolbar" aria-label="快速开始标签"`；每个标签按钮 `aria-pressed` + 状态化 `aria-label`（见 1.1） |

### 1.3 计时开始/停止的无声播报

计时是**后台持续状态**，视觉每秒都在变（大字号时钟），读屏用户无法监控。

**规范**
- 启动成功 → `role="status" aria-live="polite"` 播报 `已开始计时：编码实现`。
- 停止成功 → 播报 `已停止，本次记录 1 小时 24 分`。
- **禁止**给时钟本身加 `aria-live`（每秒播报会淹没读屏器）。时钟容器标 `aria-hidden="true"`，另设一个视觉隐藏的 `<p role="timer">`，每 60s 更新一次文本。
- 多条并行时播报要带标签名：`已停止：编码实现，本次 1 小时 24 分`。

### 1.4 备注保存（RunningTimer 1232–1245）

**现状**：点「存备注」→ 按钮文字变 `✓ 已存`，1.5s 后（`setTimeout`）变回。无错误 toast（走 `alert`）。

**规范**
- 补一个**自动保存**（输入停止 800ms 后自动保存，去掉按钮）。这是最省事的路径。
- 保留手动按钮作为显式选项。
- 反馈：按钮区显示 `已保存 14:32`（时间戳，非相对时间），持续显示不自动消失。
- 动效：保存时按钮内出现 150ms spinner；成功文字 180ms 淡入。
- a11y：保存成功 `role="status"` 播报 `备注已保存`；失败必须内联报错 + 重试按钮，不许`alert`。
- **注意**：当前 `useEffect` 里 `setTimeout(() => setNoteSaved(false), 1500)` 没有 cleanup，组件卸载后 setState 会警告。规范要求改成 `useRef` 存 timer 并在 cleanup 里 `clearTimeout`。

### 1.5 快捷键（新增，见A11Y_RESPONSE.md §2 完整表）

计时页必须支持：
- `Space` — 停止/开始「当前选中的标签」（需先有选中态，见下）
- `1`–`9` — 直接启动对应可见标签按钮
- `T` — 打开「写新记录」快速弹层
- `Esc` — 关闭任何弹层

**为了让快捷键可达，快速开始需要「选中」概念**：当前是"点一下就启动"，没有"先选中再启动"的两段式。建议引入**键盘焦点即选中**（roving tabindex），Tab 进入快速开始容器时第一个标签自动获得焦点，`1`–`9` 对应容器内可见的第 N 个按钮。**鼠标点击行为不变**（仍然一点就启动），仅键盘走两段式。这样不破坏现有肌肉记忆，又让键盘可用。

## 2. 事项 / 待办（TodosPage）

### 2.1 完成勾选（TodoCard 492–504）

**现状**：点圆圈 → `toggle(id)`。若已完成 → `window.prompt('请填写恢复未完成的原因')`；若超时 → `window.prompt('这项活动已经超时，请填写原因')`。成功后 `load()` 全量重拉（119–131 行）。

**问题**：
1. **`window.prompt` 是浏览器原生弹窗**，样式不可控、在 Capacitor WebView 里体验割裂、无法自定义校验提示。这是本项目最多的原生弹窗（TodosPage 2 处 + TimerPage 3 处 prompt + 全项目 12+ 处 `confirm`/`alert`）。
2. `load()` 全量重拉 → 整个列表闪一下（无任何过渡）。
3. 完成后条目**瞬间从"未完成"消失**（因为默认 `statusView='pending'`），用户看不到"我完成了什么"的确认。

**规范**

| 步骤 | 规范 |
|---|---|
| 触发（正常完成） | 点圆圈 |
| 反馈 | 乐观更新：圆圈立刻变绿打勾（120ms），**条目 600ms 后才开始淡出移出**（240ms opacity+height），淡出结束后焦点移到"下一条待办"的圆圈（不是跳回顶部）。右上角 toast：`已完成：评审 UI 一致性` + `撤销` 按钮（保留 5s） |
| 动效 | 勾选 120ms；条目移出 240ms 延迟 600ms；焦点移动瞬时 |
| a11y | 圆圈 `role="checkbox" aria-checked` + `aria-label="完成活动：{title}"`；移出后 `role="status"` 播报 `已完成：{title}`；`撤销`按钮需可聚焦 |

| 步骤 | 规范 |
|---|---|
| 触发（超时完成） | 点圆圈，且 `todo.dueDate < now` |
| 反馈 | **替换 `window.prompt`** 为 `ModalShell`（复用 TimerPage 已有的 `ModalShell` 组件，TimerPage 1908 行）内联弹层：标题`这项活动已超时`，textarea `placeholder="例如：需求变更未完成，顺延到明天"`，`minlength=2`；主按钮`确认完成` / 次按钮`取消` |
| 动效 | 弹层 200ms `modal-in`（复用现有 `--ui-ease`），overlay 150ms 淡入 |
| a11y | `role="dialog" aria-modal="true"`，`aria-labelledby` 指向标题；打开时焦点入 textarea；焦点陷阱在内；`Esc` = 取消且**不改变任何数据**；提交失败时错误 `role="alert"` 挂在 textarea 下方并 `aria-describedby` |

| 步骤 | 规范 |
|---|---|
| 触发（恢复未完成） | 同上，弹层文案 `请填写恢复未完成的原因`；空内容时主按钮 disabled + 提示"原因不能为空"（**前置禁用，不要点了才报错**） |

**批量操作（新增）**

**现状**：完全没有。用户要完成 10 条必须点 10 次。

**规范**
- 长按（移动端 500ms）或行首 checkbox 旁新增一个选择框，进入「多选模式」。
- 进入多选模式后，吸顶表头（TodosPage 246 行已有一个 `sticky top-0` 的表头，正好复用）右侧浮出操作条：`已选 N 项` + `完成` + `移动到…` + `改优先级` + `删除` + `退出`。
- 移动端：长按不冲突于滚动，因为 `touch-action` 默认允许滚动；实现上需在 `onTouchStart` 用定时器 + `onTouchMove` 取消。
- a11y：多选模式下每个圆圈变为 `role="checkbox"`，`Shift+点击` 支持区间选择；`Escape` 退出多选；批量操作按钮 `aria-label="批量完成已选的 3 项"`。

### 2.2 新建（quickAdd 142–152, 324–338）

**现状**：`+ 新建活动` 按钮展开一个 input + 「添加」按钮，回车提交。**只能创建标题**——没有优先级、没有分类、没有循环、没有截止日期。要设这些必须先点「+新建」再点某条的「编辑」。

**问题**：新建待办是高频动作，但快速路径只能填标题，导致大量待办是「无分类、无循环、无优先级」的三无数据，事后又要点进编辑弹层补。这是**数据质量下降的根因**。

**规范**
- 保留极简快速添加，但增加**语法后缀**（Todoist 模式）：输入 `写周报 p1 #工作 !2/20`，回车后自动解析出优先级/分类/截止。解析失败时**不报错**，原样保留标题并在行尾显示一个 `⚙` 标记，hover/focus 显示"未识别：#工作"。
- 展开的输入框旁加一行 chip 提示：`p1 优先级 · #分类 · !日期`。
- a11y：语法提示必须对读屏用户可见（不能只靠 placeholder）；`role="status"` 播报解析结果 `已创建：写周报，重要，工作，截止 2 月 20 日`。
- 移动端：`+ 新建活动` 应**吸底**（`position: sticky bottom-0`），因为快速开始/列表上方在移动端可能需要滚动。

### 2.3 编辑（TodoEditModal 614–775）

**问题（严重）**：整个弹层
- **没有 `role="dialog"`**、没有 `aria-modal`、没有 `aria-labelledby`（对比：TagsPage 的 `Modal` 组件 565–587 行有完整标注）。
- **没有焦点陷阱**，`Esc` 不能关闭（TagsPage 的 Modal 有 `Escape` 监听，567–573 行）。
- 关闭后**焦点不回到触发按钮**。
- `<label className="block text-sm text-gray-5xx">标题</label>` 与 `<input>` **没有 `htmlFor` / `id` 关联**（669行等）—— 点label 不会聚焦输入框。

**规范**
- 统一到 `ModalShell`（TimerPage 1908 行已有），补齐：`role="dialog" aria-modal="true" aria-labelledby={id}`、焦点陷阱、`Esc` 关闭、`useRef` 记录 opener 并在关闭后 `focus()`、背景 `inert`。
- 所有字段加 `id` + `htmlFor`。优先级/状态的按钮组改 `role="radiogroup"` + `role="radio" aria-checked`（当前是普通 button，视觉像radio 但语义不是）。
- 底部「保存」在 `title` 为空时 **disabled + 显示原因**，不要点了才弹错误（当前 635–639 行是点了才 `setError`）。
- 移动端从底部弹出（现在 TodosPage 的弹层是 `items-center` 居中，PlansPage 的已经是 `items-end ... sm:items-center` 底部抽屉 —— **统一为 PlansPage 的底部抽屉形态**）。

### 2.4 删除（remove 191–199）

**现状**：`window.confirm('确定删除这条待办吗？')`。删除后 `load()` 全量重拉。

**规范**
- 删除待办**不弹 confirm**（可从 toast 的 `撤销` 恢复即可，见2.1）。改为：条目立刻移除 + toast `已删除：{title}` + `撤销`（保留 8s，`撤销` 调用重新创建）。
- 删除习惯打卡记录（已完成项）**必须二次确认**，因为它携带 `lateReason` / `restoreReason` 等审计信息——这类数据删除应走 `ModalShell` 的确认弹层并**要求输入删除原因**（与项目里"终止链路必须填原因"的既有约定一致）。
- a11y：删除成功 `role="status"` 播报 `已删除：{title}`，焦点移到列表中同位置的相邻项。

### 2.5 筛选与搜索（289–322）

**规范**

## 3. 事项 / 习惯（GoalsPage）

### 3.1 补上打卡能力（**最高优先级**）

**现状**：GoalsPage **零按钮**（grep 确认）。打卡在别处。

**规范**：`tracking` 目标（次数/时长型）与 `activity` 目标（活动型）都要能在此打卡。

| 目标类型 | 打卡控件 | 触发 | 反馈 | 动效 | a11y |
|---|---|---|---|---|---|
| `tracking` + `type='count'` | 大号圆形打卡按钮（直径 ≥56px），显示 `3 / 8次` | 点击 | 计数 +1，进度条推进，数字 1.2s 翻倍；若本次是「补打卡」（非当天），显示"补 3/12" | 圆环 `stroke-dashoffset` 240ms `--ui-ease`；数字翻倍 240ms | 按钮 `aria-label="给{标题}打卡，当前 3/8 次"`；播报 `已打卡：每日读书，4/8 次` |
| `tracking` + `type='time'` | 显示 `已累计 128 / 200 分钟` + 引导按钮 `去工作台计时` | 点击引导 | `Link to="/"` | — | 播报当前进度 |
| `activity` | 列表项 + 圆圈勾选，复用TodosPage 的圆圈 | 点击 | 同 2.1 | 同 2.1 | 同 2.1 |

**风险标注（高风险交互）**：`tracking` 打卡若需要新增 API，属于 Server 改动，**超出授权范围**。

### 3.2 连续天数（当前完全没有）

**规范**：每个目标卡片右侧加**连续天数徽章**。

- 视觉：`🔥 连续 5 天`；`🔥 5 天` = 连续达标，`⏳ 今天还没打卡` = 断档，`—` = 无历史。
- **颜色不能是唯一载体**：徽章必须有文字 + 图标，色弱用户能读懂。
- 连续 ≥7 天用 `🔥`，≥30 天加 `⚡`，避免"连续 6 天"和"连续 60 天"视觉上没有区别。
- a11y：`aria-label="已连续 5 天达标"`。

### 3.3 进度可视化

**现状**：进度条有 `role="progressbar"` 且 `aria-valuenow/max/min` 完整（76 行）——**这是全项目 a11y 做得最好的组件，保留**。

**不足**：进度条归一化到 `percent = current/target`，超过 100 就满了。无法表达"超额"。

**规范**
- 进度条保留，右侧数字 `${current} / ${target} ${unit}` 保留。
- 达标（`current >= target`）时整卡加 `ring-1 ring-emerald-500/40` + 左侧 `✓` 图标（**不只靠 `text-emerald-600` 的数字变色**——当前 74 行只改文字颜色）。
- 数字用 `tabular-nums`（当前没有），避免数值跳动时宽度抖动。

### 3.4 拖拽排序的无障碍替代

**现状**：`draggable` + `onDrop`（61–67 行）。**纯鼠标操作，键盘与触屏用户无法排序**。移动端 HTML5 drag-and-dnd 基本不可用。

**规范**
- 每个 `article` 内的 `GripVertical`（当前 70行）改为**可聚焦按钮**：`tabIndex={0}` `aria-label="拖动排序：{标题}，当前第 {i+1} / 共 {n} 项"`。

- **触屏兜底**：`GripVertical` 点击 → 弹出 `ModalShell` 内列表 `上移 / 下移 / 移到最前 / 移到最后`。
- TagsPage / TimerPage 快速开始的三处拖拽同理。这是**必须项**，不是可选优化。

## 4. 时间 / 日历（CalendarPage）

### 4.1 视图切换与日期切换

**现状**（CalendarPage 495–634）：工具栏含`‹` `›`（无 aria-label！）、`今天`、标题 `<h1>`、`新建计划`、`新建记录`、合计、类型筛选（全部/计时/活动）、分类筛选 popover、月/周/4天切换、`🗓️` 日历同步、`📡` 订阅管理。

**问题**
1. `‹` `›` 按钮**没有 `aria-label`**，读屏用户只听到"按钮"。同理 `🗓️` / `📡` 只有 `title`（title 在触屏上不显示，且不是可靠的 a11y 名称——部分读屏器忽略 title）。
2. 月/周/4天切换是三个普通 button，**没有 `aria-pressed`**。
3. 「全部/计时/活动」筛选同样没有 `aria-pressed`。
4. 视图状态（`view`）和当前日期（`currentDate`）都是 `useState`，**不进 URL** → 无法分享"我看的是 3 月 15 日那周"，刷新回到今天。

**规范**

| 项 | 规范 |
|---|---|
| 无障碍名称 | `‹` → `aria-label="上一${viewLabel}"`（"上一周"/"上个月"）；`›` → "下一${viewLabel}"；`🗓️` → `aria-label="日历同步设置"`；`📡` → `aria-label="外部日历订阅管理"`。**emoji 一律加 aria-label 或 `aria-hidden` + 兄弟文本** |
| 视图切换 | 三个按钮包在 `role="tablist" aria-label="日历视图"`，每按钮 `role="tab" aria-selected`（复用 SectionPage 模式），或至少加 `aria-pressed`。切换后焦点移到新激活的 tab |
| 视图-日期联动 | 切视图时保持"当前聚焦日期"不变：`2026-03-15` 在月视图切到周视图 → 显示 3/9–3/15 这一周（当前 `startOfWeek` 的实现应已如此，需验证，见 §7 待验证项） |
| URL 同步 | `?view=month\|week\|four` + `?date=2026-03-15`。`view=month` 为默认则省略，`date` 为今天则省略（与 `SectionPage` 的"首tab 不写参数"同一策略）。用 `useSearchParams` 的 `replace: false`（用户主动切换要进历史栈，浏览器返回键应能回到上一个视图） |
| 触达尺寸 | `‹` `›` 当前 `w-9 h-9` = 36px < 44px。改为 `h-10 w-10`（40px）配合工具栏 `py-1`，或用伪元素扩大到44px 触达区 |

### 4.2 事件创建（新建计划 / 新建记录）

**规范**
- 两个按钮都已有，保留。移动端工具栏横向滚动（526 行 `overflow-x-auto`），但「新建记录」是主按钮，被挤在滚动区右侧，**在移动端第一屏可能看不到**。

### 4.3 跨天数据呈现

**现状**：DayView / WeekView / MonthView 三套视图。`layoutEntries`（192 行）做重叠布局。跨天由 `externalEventRange`（122 行）和 `activityIsOnDay`（165 行）处理。

### 5.1 加载态（**当前最严重的问题**）

**现状**：StatsPage `entries`/`plans` 初始 `[]`，`useEffect` 里 `Promise.all` 拉数据。**没有任何 `loading` 状态**（读全文 126 行确认）。

**规范**：详见 `EMPTY_LOADING_ERROR.md`。核心：引入 `status: 'loading' | 'ready' | 'error'`，加载时用骨架屏而非空态文案。

### 5.2 图表交互

**现状**（StatsPage 53–97）：

| 周期切换 | `<select aria-label="统计周期">` ✓ 已标注。规范：改为与日历页一致的 pill按钮组 + `aria-pressed`，并写入 URL `?range=weekly` |

## 6. 体系 / 标签（TagsPage）—— 视觉分色的数据基础

**这一节的规范直接决定 Phase 1 视觉系统的分色能否落地。**

### 6.1 现有色板的问题

```tsx
// TagsPage.tsx 8 / 525（两处重复定义，值完全相同）
const COLORS = ['#0f766e','#ef4444','#f59e0b','#10b981','#3b82f6','#ec4899','#8b5cf6','#14b8a6','#64748b']
const PRESET_COLORS = [...完全相同...]
```

9 个预设色的问题：
1. **`#0f766e`（teal-700）与 `#14b8a6`（teal-500）在亮色底上极难区分** —— 两者都在同一个色相族，色相几乎相同，明度差 2 档。用户给"工作"和"生活"分色时如果各选一个，视觉上分不开。
2. **`#10b981`（emerald-500）与 `#14b8a6`（teal-500）** —— 绿色 vs 青绿，也是邻近色相。
3. **色盲友好性未验证**。`#f59e0b`（amber）与 `#10b981`（emerald）在 deuteranopia（红绿色盲，最常见，约 6% 男性）下会变成**几乎相同的黄褐色**。8 个色点里有 2 对会撞。
4. **对比度未验证**。`#f59e0b` 在白底上对比度约 2.1:1，**低于 WCAG AA 对文本的 4.5:1 与对图形元素的 3:1**。而标签名在多处是用标签色作为文字颜色的（如 `TodosPage` 278 行 `style={{ color: goal.tag?.color }}`、`StatsPage` 色点旁、TodosPage 分类徽标 524 行 `color: todo.category.color`）。

**→ 标签色当前被同时用作「背景块」「色点」「文字颜色」三种角色，而色板只保证了色相区分，没有保证对比度。这是视觉分色落地前必须修的地基问题。**

### 6.2 新色板规范

> **⚠️ 与视觉团队的对齐说明（2026 复核第 3 次，数值全部重测）**
> 视觉团队的 `docs/design/.generated-palette.css` 由 `scripts/design-tokens.mjs` 生成，**已被重新生成过三次**。我初稿引用的 hex 已全部失效，本节数值以本次重新读取 `.tokens-report.json` + `.generated-palette.css` 后**脚本实测**为准。当前产物：
>
> | 组 | 内容 | 职责 |
> |---|---|---|
> | `--domain-{work,time,tasks,insights,system}-50..900` | 5 组 10 档域色阶 | **导航域氛围色**（一级入口的界面气质） |
> | `--n-0..950` | 12 档中性阶 | 文本/边框/背景 |
> | `viz-1..viz-6`（**仅存在于 `.tokens-report.json`，未输出到 `.generated-palette.css`**） | 6 色**分类数据色板** | **数据可视化 / 分类标识** ← **这才是标签色的正主** |
>
> **修正我初稿的判断**：初稿说"视觉没有标签色板、我需派生 10 色"，这个判断**已过时**——`viz-*` 就是为此设计的。**本节改为：以 `viz-*` 为基础，只做对比度补强与暗色配对，不另造色相。**
>
> **两次复核间的变化（需视觉确认是否有意）**：`viz-*` 从 **8 色缩减为 6 色**（原 teal/amber/indigo/rose/violet/cyan/lime/slate → 现 red/orange/green/cyan-blue/indigo/magenta）；`time-600` 已按此前的不达标结论压暗为 `#656EC5`；`.tokens-report.json` 的 `failures` 现为**空数组**。

**现状色板的三类硬伤（已量化）**

```
COLORS = ['#0f766e','#ef4444','#f59e0b','#10b981','#3b82f6','#ec4899','#8b5cf6','#14b8a6','#64748b']
```

1. **9 个预设里有 2 组会在红绿色盲（deuteranopia，约 6% 男性）下撞车**：`#f59e0b`(amber) 与 `#10b981`(emerald) 模拟下均为同一黄褐；`#ef4444`(red) 与 `#ec4899`(pink) 均向黄褐偏移。
2. **`#f59e0b` 白底对比度仅 2.15:1**（实测），远低于 AA 文本 4.5:1。而标签色当前被用作**文字颜色**（`TodosPage` 278 行 `style={{color: goal.tag?.color}}`、`TodosPage` 524 行分类徽标 `color: todo.category.color`）。
3. **暗色模式下标签色不变**：`#0f766e` 在最暗底 `#0C0C20` 上仅 **3.52:1**（实测）——标签色没有随主题切换。

**`viz-*` 色板的实测门槛（2026 复核，脚本实测）**

| token | Hex | HSL | 白底对比度 | 色块 3:1 | 文字 4.5:1 | 暗底 gray-800 | 暗底 gray-950 |
|---|---|---|---|---|---|---|---|
| viz-1 | `#AC402E` | 9° 58% 43% | 5.95:1 | ✓ | ✓ | 2.47:1 | 3.38:1 |
| viz-2 | `#DE723A` | 20° 71% 55% | 3.19:1 | ✓ | ✗ | 4.60:1 | 6.30:1 |
| viz-3 | `#69A13F` | 94° 44% 44% | 3.10:1 | ✓ | ✗ | 4.73:1 | 6.49:1 |
| viz-4 | `#009CD8` | 197° 100% 42% | 3.11:1 | ✓ | ✗ | 4.72:1 | 6.47:1 |
| viz-5 | `#6767C2` | 240° 43% 58% | 4.89:1 | ✓ | ✓ | 3.00:1 | 4.12:1 |
| viz-6 | `#C55898` | 325° 48% 56% | 4.02:1 | ✓ | ✗ | 3.65:1 | 5.01:1 |

> **`viz-*` 是为「图表色块」设计的（3:1 门槛），不是为「文字」设计的。6 色里只有 2 色（viz-1/viz-5）能安全当文字色。**
> 而 ITtime 的标签色**同时**要当色点（3:1 够）和文字色（4.5:1 要，见上面第 2 条硬伤）。**这是 viz 色板与标签场景的真实缺口。**
>
> **暗色模式方向相反**：亮色下不达标的是中明度色（viz-2/3/4），暗色下不达标的反而是最暗的 viz-1（gray-800 上 2.47:1）。**同一套 hex 不可能同时伺候两个主题**，必须双档（见下）。
>
> **色盲可分性（本次新增实测，Viénot deuteranopia 模拟）**：6 色在正常视觉下的色相角为 9°/20°/94°/197°/240°/325°，**viz-1 与 viz-2 只差 11°**（已低于本文 §6.2 自定的 25° 相邻校验阈值）。红绿色盲模拟下色相进一步塌缩，**7 对色相的差值 <25°**，其中最危险的是 **viz-4 ↔ viz-5（模拟色相差 5°，都塌成蓝紫，仅靠饱和度 50% vs 30% 区分）**；viz-1/viz-2/viz-6 则同时塌向黄褐，仅靠明度差区分。
> **结论：色相不是可靠的唯一区分手段。** 图表场景必须叠加第二通道（直接数值标签 / 排序 / 形状），标签场景必须叠加文字名。**"色盲可辨"不能靠色板本身保证。**

**规范：`viz-*` 作色块 + 每个色配一个 `-ink` 文字档**

标签色在数据结构上**存两个值**（或存一个 token 名，渲染时映射）：

| 角色 | token | 用途 | 门槛 |
|---|---|---|---|
| **色块/ 描边 / 进度条** | `viz-N` | 色点、日历色块、排行条、图表 | ≥3:1 ✓ 6 色全部满足（3.10–5.95） |
| **文字色 `-ink`** | 见下 | 标签名文字、徽标文字、图表轴标签 | ≥4.5:1 |

### 6.3 颜色赋予的交互规范

**现状**（ColorPicker 527–562）：
- 原生 `<input type="color">`（10×10rem = 40px）
- hex 文本输入（`.input !w-32 font-mono`）
- 9 个 24×24px 预设色按钮，`title={c}`，选中态用 `ring-2 ring-offset-1 ring-gray-400`

**问题**
1. **24×24px 的色块触达区远小于 44px**。触屏上极难点中，且色块之间只有 6px（`gap-1.5`）间隔。
2. **预设色按钮没有 `aria-label`**（只有 `title`）。读屏用户听到的是按钮名称为空。
3. **选中态只有 `ring`**（灰环 `--gray-400`）—— **不是颜色**。在色弱用户的屏幕上，选中/未选中可能完全分不出。
4. hex 输入**无实时校验**：输入 `#ZZZZZZ` 会被当合法值传下去（`onChange` 直接 `onChange(e.target.value)` 无校验）。
5. 原生 `<input type="color">` 在 Capacitor WebView 里体验不保证。

**规范**

```
┌─ 颜色 ────────────────────────────────────────┐
│                                               │
│  预设色（6 色 = viz-1..viz-6，2 行 × 3 列）      │
│  ┌────┬────┬────┐                              │
│  │ ●  │ ●  │ ●  │  44×44px 触达                 │
│  ├────┼────┼────┤  视觉 28px 圆点               │
│  │ ●  │ ●  │ ●  │  gap 8px                      │
│  └────┴────┴────┘                              │
│                                               │
│  ○ 十六进制   [ #0f766e ]  [复制]             │
│  ┌──────────────────────────────────────┐   │
│  │  色彩预览条（当前色的 12% / 40% /100%）  │   │
│  └──────────────────────────────────────┘   │
│                                               │
│  文字颜色预览  文字颜色预览  ← 演示该色作前景   │
└───────────────────────────────────────────────┘
```

| 项 | 规范 |
|---|---|
| 触达 | 每个色块**触达区 ≥ 44×44px**（用 `p-2` 外扩或伪元素），视觉圆点 24–28px，槽间 gap ≥ 8px |
| 选中态三重信号 | ① `aria-pressed` / `role="radio" aria-checked`；② **形状变化**：选中圆点外扩 1.5px 并加2px 实心白环（`box-shadow: 0 0 0 2px #fff`），非颜色依赖；③ **✓ 勾号**（深色/浅色文字以保证可见） |
| 无障碍名称 | `aria-label={`${色名}，${c}`}`，如 `aria-label="砖红，#AC402E"`（色名用语义名，不要用 `viz-1` 这种内部 token 名） |
| 键盘 | 色块容器 `role="radiogroup"`，`←`/`→`/`↑`/`↓` 移动选择，`Space`/`Enter` 选中。**移动端上下箭头 44px 槽位意味着上下移动会跨 5 格**，需实测 |
| hex 校验 | 输入时实时校验 `#RRGGBB`，非法则输入框 `aria-invalid="true"` + 红边 + 下方文字"请输入 6 位十六进制色值"，**且不更新预览与保存值** |
| 对比度守卫 | 选择时**实时计算**该色对当前背景（亮/暗）的对比度，若 < 3:1 提示 `该颜色在当前主题下对比度较低，建议加深`（黄色 `role="status"`），但**允许用户强行选择**（不阻断创作自由） |
| 原生取色板 | 保留，但降级为"自定义"入口，位置在预设色下方，标注 `自定义` |
