## 结论先行

这个项目的**设计系统规范质量很高**（4518 行设计文档、OKLCH 感知均匀色板脚本、构建后域色回归校验），
实测的视觉完成度也明显高于一般个人项目：毛玻璃侧栏、极光背景、域色分色、暗色分流都做得很精致。

但实测暴露了**三个此前未被记录的真实问题**，其中一个是会直接影响观感的严重回归。

### 实测发现的三个关键问题

1. **P0：暗色模式下侧栏/底部导航激活态几乎不可见（对比度 1.07:1）**
   实测确认：侧栏「事项/时间/洞察/标签」激活态 **1.33–1.34:1**，
   底部「待办」tab **1.07:1**，侧栏「工作台」**2.72:1**（WCAG 1.4.3 要求 ≥4.5:1）。
   根因已定位到行：`SectionPage.tsx:72` 与 `Layout.tsx:51,57` 的激活态写了 `bg-brand-50`
   但**没配 `dark:` 覆盖**——全项目其他 14 处 `bg-brand-50` 都规规矩矩配了
   `dark:bg-brand-900/30`，只有这 3 处漏了。**修复已实测验证：1.07 → 16.07。**

2. **P0：`page-in` 的 transform 残留导致所有 fixed 弹窗错位（回归）**
   团队在 commit `7c46939` 修过这个 bug，但**当前代码已回归**：
   `tailwind.config.js:181` 的 `animation: page-in 300ms ... both`，
   `fill-mode: both` 让 `<main>` 的 transform 永久停在 `matrix(1,0,0,1,0,0)`，
   使其成为 fixed 定位的 containing block。实测 overlay `1174×616@266,23`
   而非 `1440×900@0,0`——**全站弹窗遮罩都偏移**。

3. **P1：笔记模块（约 1700+ 行）完全不可达**（静态扫描发现，非实测）
   `NotesPage` / `NoteEditorPage` / `VaultPage` / `NotesGraphPage` 均已实现，
   但 `App.tsx:229` 里 `/notes/*` 直接 `Navigate to="/"`，零引用。

## ⚠️ 三条被实测推翻的初版结论（务必先读）

本报告初版基于静态扫描，有三条推断被后续实测证伪。**已按实测结论修正，请勿再沿用初版判断。**

### ① 中性色断层：从 P1 降为 **P3**，且「重新标定后再迁移」的建议也需要改

**初版判断**：这是最严重的一致性问题，建议 codemod 迁移。
**实测结论**：**肉眼几乎不可感知，不构成视觉缺陷。**

评审专家从**实际渲染结果的 computed style** 取样（不是查色板），换算到 OKLCH：

| 角色 | hex | L | **C（色度）** |
|---|---|---|---|
| 页面底色（亮） | `#f8fafc` | 98.4 | **0.003** |
| 边框（亮） | `#e5e7eb` | 92.8 | **0.006** |
| 次要文字 | `#9ca3af` | 71.4 | **0.019** |
| 页面底色（暗） | `#030712` | 13.0 | **0.027** |

人眼在明亮背景上可分辨的色度阈值约 **C > 0.03–0.04**，而这些中性色的 C 值
**全部低于或贴着该阈值**——所以"冷倾 vs 暖灰"的差异在实际观感中不可见。

更关键的实测数据（on `#edf2f8`）：

| 档位 | gray（在用） | n-*（定义未用） | 谁更好 |
|---|---|---|---|
| 400 | **2.26:1** | 1.69:1 | **gray 胜** |
| 600 | **6.71:1** | 4.03:1 | **gray 胜** |
| 800 | **13.04:1** | 10.81:1 | **gray 胜** |

**`n-*` 色阶比 `gray` 更浅，对比度全面更差。**
`n-400 #bbbc c6` 的 L=79.5 vs `gray-400` L=71.4——`n-*` 被设计成"更淡更柔"，
但项目实际把它当正文色用（注释写的是"替代 gray/slate 混用"）。

**修正后的建议**：这**不是** P1，甚至不是 P2。

- ❌ 不要做 codemod 迁移（会让对比度变差）
- ❌ 不要花时间"重新标定 n-* 色阶"（当前视觉无缺陷，投入产出极低）
- ✅ **最划算的动作是改 `tailwind.config.js:45` 的注释**——
  那里写着「中性色阶 n-*：替代 gray/slate 混用，统一冷倾」，
  描述了一个**未实现且不该实现**的意图，会误导后续维护者
- ✅ 或者直接**删掉 `n-*` 定义**，别留一个"看起来该用但用了会错"的陷阱

## P0 · 阻塞级

### P0-1 暗色模式侧栏激活态对比度 1.07:1（实测确认）

**实测复现**：
- 条件：暗色主题 + 侧栏「体系」域（`--d-system-400` = `#D3889C` 紫玫瑰）
- 激活项文字：`text-brand-200` → `#F6C6D2`
- 激活项底色：`bg-brand-500/15` 叠加紫玫瑰玻璃 `--sidebar-bg: rgba(20,32,50,.28)`
- **实测对比度：1.07:1**（WCAG 1.4.3 正文要求 ≥4.5:1，1.4.11 非文本要求 ≥3:1）

**实测原文**：
> "侧栏激活项形同消失：'标签'的紫玫瑰色文字落在紫玫瑰色玻璃底上，肉眼几乎不可见，
> 用户在暗色下无法判断当前所在页面。"

**根因**：`text-brand-200` 是**固定档位**，不随暗色切换；而底色用
`bg-brand-500/15`（半透明域色）叠在同样带域色的玻璃上，
两者的色相锚定在同一个 `--d-system`，明度却只差 7%。

**这是全局问题**：暗色模式下访问「标签」「设置」「洞察」等所有 `d-400` 亮度偏低的域，
都会出现同类问题（system 域最严重，insights 域次之）。

**建议修复**（在 `Layout.tsx`）：
把激活态文字从固定档位改为**角色变量**：

```tsx
// 当前（问题）
'text-brand-800 ... dark:text-brand-200'

// 建议：改用随主题分流的角色变量
// index.css 已有定义好的角色变量：
//   --d-fg  → 亮色 = 700 档（白底 ≥4.5:1）
//             暗色 = 300 档（深底高对比）
'... dark:text-[rgb(var(--d-300-rgb))]'
```

即暗色下用 `--d-300`（比 `--d-200` 更亮、更高对比），而非 `--d-200`。
同时底色的半透明度建议从 `/15` 降到 `/10`，或改用 `--d-bg`（暗色下是 `rgb(var(--d-900-rgb)/.45)`）
这类专门为暗底设计的角色变量，避免"域色叠域色"。

**验证方法**：修复后用实测脚本重算对比度，目标 ≥4.5:1。

### P0-2 `page-in` transform 残留导致 fixed 弹窗错位（回归，实测确认）

**实测复现**：
1. 打开 `/tasks?tab=todos` → 编辑任一待办
2. 实测弹窗容器矩形：`266, 23, 1174, 616`
3. 实测视口矩形：`0, 23, 1440, 878`
4. **遮罩明显缩进，未覆盖全屏**（与实测截图一致）

**根因（这是一个已修复过的回归）**：

`apps/web/tailwind.config.js`：
```js
'page-in': {
  from: { opacity: '0', transform: 'translateY(12px) scale(.99)' },
  to:   { opacity: '1', transform: 'none' },
},
// ...
'page-in': 'page-in 300ms cubic-bezier(.16,1,.3,1) both',
//                                          ↑ 这里
```

代码注释里写得很清楚：`animate-page-in` 挂在 `<main>` 且 **fill-mode 为 `both`** 时，
若 transform 常驻，`<main>` 会成为 containing block，页内所有 `fixed` 弹窗的
`inset-0` 变成相对 `main` 定位，遮罩只剩内容区高度。

commit `7c46939`「修复弹窗遮罩半屏」正是为此，但当前 `both` 又回来了
（可能是后续 `361f612`「动效体系落地」时改回，或从别处合并引入）。

**为什么注释里的 `transform: none` 不管用**：
`transform: none` 在**动画进行中**仍会插值出矩阵值，300ms 后才回到 none；
但 fill-mode `both` 会把结束状态也保留在元素上。更关键的是——
只要元素在动画的**任一时刻**具有非 none 的 transform（哪怕是运行中的插值态），
它就会成为 fixed 定位的 containing block。实测证明该风险窗口依然存在。

**建议修复**（三选一，从优到劣）：

1. **改 fill-mode**（最小改动）：
   ```js
   'page-in': 'page-in 300ms cubic-bezier(.16,1,.3,1) forwards',
   ```
   `forwards` 同样保留结束帧，效果一样——**所以这一条单独用不够**。

   真正干净的做法是**把动画挂到 `<main>` 的内层容器**，而不是 `<main>` 本身：
   ```tsx
   // Layout.tsx:68 当前
   <main key={location.pathname} className="app-main ... motion-safe:animate-page-in">
   ```
   改为
   ```tsx
   <main className="app-main ...">
     <div key={location.pathname} className="motion-safe:animate-page-in">{children}</div>
   </main>
   ```
   这样即使 transform 常驻，受影响的也只是内层 div，`fixed` 弹窗仍相对视口定位。

2. **弹窗改用 Portal**（最正确）：`CalendarPage` 已经用了 `createPortal`，
   把所有弹窗统一 Portal 到 `document.body`，彻底摆脱任何祖先 transform 干扰。
   项目已有先例，改造可行，但工作量最大。

3. **加回归测试**：把这条写进 `scripts/verify-domains.cjs` 或新建校验脚本，
   断言构建产物中 `animate-page-in` 不带 `both`。

**建议采用 1 + 3**：改动小、风险低，且加测试防止再次回归。

### P0-3 笔记模块完全不可达（功能已开发但用户无法访问）

> **发现来源：静态扫描**（grep 路由引用），**非浏览器实测**。
> 评审专家实测时未打开这四个页面，因此本条无浏览器实测证据，
> 但证据链确定：`App.tsx` 中不存在指向它们的路由，且全项目零引用。

**证据**：`apps/web/src/pages/` 下存在 4 个已实现的笔记相关页面：

- `NotesPage.tsx`（429 行）
- `NoteEditorPage.tsx`（670 行）
- `VaultPage.tsx`（826 行）
- `NotesGraphPage.tsx`（373 行）

合计约 **2298 行**已开发代码，外加 `editor/` 目录下 CodeMirror + KaTeX + marked 整套编辑器栈。

但 `App.tsx` 的路由表中：
```
<Route path="/notes/*" element={<Navigate to="/" replace />} />
```
这 4 个页面**从未被任何路由引用**（grep 全项目，零引用）。
旧笔记书签被直接重定向到计时页，用户完全无法触达。

**影响**：
- 用户视角：功能不存在，但代码库承担了全部维护成本
- 首屏视角：这些页面未被 lazy 引入，不影响主包（但见 P1-3）
- 演进视角：Roadmap 中无笔记条目，说明这不是"即将上线"，而是"做完了没接上"

**建议**：明确二选一——
- **接线**：在导航中给笔记一个入口（建议并入 `/time` 分区或新增一级入口），补路由
- **下线**：移出 `pages/`，保留 `editor/` 供未来复用，避免僵尸代码

考虑到用户诉求是"更便捷"，且笔记模块投入产出已存在，**建议接线**。

## P1 · 严重级

### P1-1 中性色令牌断层：1489 处 `gray-*` 绕过了设计系统

**证据**：

- `tailwind.config.js` 定义 `colors.n`（`n-0` … `n-950`，OKLCH hue 240 冷倾）
- `index.css` 定义 `--n-0-rgb` … `--n-950-rgb` 全套 RGB 三元组
- 实测 `.tsx` 中 `n-*` 使用次数：**0**
- `gray-*` 使用次数：**1489**，`slate-*` 4 处

**实测观察（评审专家在 1024px 下的实测记录）**：
> "日历选中日铺满 `--d-time-500`(#656EC5)，配白字对比度 5.56:1，视觉冲击极强，
> 整月视图被一整块高饱和紫蓝压住，相对月度数据本身过于抢眼。"

这说明问题不止于"色温不统一"——**部分强调色的使用强度也缺乏节制**。

同时 `body` 仍写死 `@apply bg-slate-50 dark:bg-gray-950`，`.app-shell` 写死 `#f8fafc`
与 Aurora 主题的 `--shell-bg`（`#edf2f8` / `#070b14`）三处背景来源打架。

> ⚠️ **本节结论已被实测推翻，级别从 P1 降为 P3，请读"结论先行"的修正说明。**
>
> 初版建议"用 codemod 把 `gray-{n}` → `n-{n}`"是**错误的**。
> 实测从**渲染结果的 computed style** 取样后换算 OKLCH，发现：
>
> - 实际生效的中性色 C 值仅 **0.003–0.030**，全部低于人眼可辨阈值（约 0.03–0.04），
>   **肉眼几乎不可感知冷暖差异**
> - `n-*` 色阶比 `gray` **更浅**，三档实测对比度全面更差（gray 400/600/800 分别 2.26 / 6.71 / 13.04，
>   `n-*` 对应 1.69 / 4.03 / 10.81）
>
> 因此这是**代码一致性问题，不是视觉缺陷**。

**修正后的建议**：

1. ❌ **不要做 codemod 迁移**（会让对比度变差）
2. ❌ **不要花时间重新标定 `n-*` 色阶**（当前视觉无缺陷，投入产出极低）
3. ✅ **改 `tailwind.config.js:45` 的注释**——那里写着
   「中性色阶 n-*：替代 gray/slate 混用，统一冷倾」，
   描述了一个**未实现且不该实现**的意图，是最可能误导后续维护者的地方
4. ✅ 或者直接**删掉 `n-*` 定义**，不留"看起来该用但用了会错"的陷阱
5. 真正值得处理的是**背景来源打架**：`body` 的 `bg-slate-50 dark:bg-gray-950`
   与 `.app-shell { background: #f8fafc }` 与 Aurora 的 `--shell-bg`
   （`#edf2f8` / `#070b14`）三处并存，统一到 `--shell-bg` 单一真相源

**关于实测提到的对比度失败项**：数量巨大但**归因未完成**。
需要注意一个反直觉的事实：既然当前代码用的是 gray（不是 n-*），
那么那些失败**不能用"`n-*` 偏浅"来解释**。这批失败需要单独一轮专项归因，
区分"gray 档位本身在特定底色上不够"与"设计意图就该降低对比度（如非文本图形）"。
**不建议盲目批量改。**

**证据**：

`tailwind.config.js` 定义了 L0–L4 五层共 9 个 keyframes 与对应 animation 类。实测使用量：

更关键的：**`--ease-exit` 令牌定义了，全站零使用**。


全站没有任何 exit/fade-out/scale-down 关键帧。

**实测逐帧采样（`requestAnimationFrame` + computed style）**：

| 弹窗 | 进场 | 退场 |
|---|---|---|
| 标签「+ 新建标签」 | `overlay-in` 200ms + `modal-in` 250ms | **6ms** |
| 工作台「+ 补录」 | 同上 | **10ms** |
| 待办「+ 新建活动」 | — | **未测到**（选择器不同，不作结论） |

退场第一帧即 `overlayAnim: 'GONE'`，`minOpacity` 全程 = 1——**没有任何透明度下降过程**。
问题客观存在（打开从容、关闭瞬间），但影响范围限于关闭这一瞬，**级别 P2 而非 P1**。

**实测修正：`animate-list-in` 并非零使用。**
`TodosPage.tsx:669` 已接入，且**错峰 delay 已接好**——实测到 `0s / 0.04s / 0.08s / 0.12s` 递增，
5/5 个列表项均命中。**待办列表的入场已经是渐进的，不是硬切。**

实测各列表入场实况：

| 列表 | 实测结果 |
|---|---|
| 待办列表 | ✅ `list-in` + 错峰 40/80/120ms |
| 洞察图表 | ❌ **4 个元素无任何动画**，柱子直接跳到位 |
| 日历格子 | ⚠️ 无动画，但检测到部分透明度状态 |
| 工作台时间线 | **未测到**（选择器未命中，不下结论） |

因此真正缺入场动画的是**洞察图表**（`bar-grow` 令牌已备好、零使用）、
以及待验证的工作台时间线与日历格子。

**影响**（直接对应用户"动画不够优雅"）：

1. **弹窗关闭是瞬间消失** —— 打开有 250ms 缓入，关闭却是硬切。
   这是"动效不优雅"最典型的症状：用户感知到的是"卡顿"，而非"流畅"。
2. **列表项、图表出现时是"突然出现"** —— `list-in` 只用在 TodosPage 一处，
   TimerPage 的活动时间线、CalendarPage 的日程块、GoalsPage 的习惯打卡全是硬切。
3. `press-tap` 零使用意味着按下反馈完全依赖 `index.css` 里的
   `button:active { transform: scale(.98) }` 全局兜底，缺乏分层的触感设计。

**建议**（按投入产出比排序）：

1. **先补退出动画**（最高性价比）。需要给弹窗加一个"卸载前播放"的过渡，
   React 里通常用一个 `useExitTransition` hook 或状态机：
   ```
   open → 播 modal-in（现有）
   close → 播 modal-out（新增 180ms，--ease-exit）→ unmount
   ```
   注意：不要用 `AnimatePresence` 引入新依赖，手写状态机即可，成本很低。
   13 处 `modal-panel` + 36 处 `fixed inset-0` 都能受益。

2. **给高频列表加 `list-in` 错峰入场**。TodosPage 已有现成范式（260ms + 5×40ms 封顶），
   复制到 TimerPage 时间线、日历日程、习惯打卡。

3. **给图表加 `bar-grow`**。Recharts 无法直接用 CSS keyframes 驱动柱状生长，
   但 `useChartMotion` 已在统一控制参数，可在此基础上调优（如 `animationDuration`
   700ms 是否偏慢、`animationBegin` 错峰是否够）。

4. **`press-tap` 用于主要按钮**，替代全局 `scale(.98)` 兜底，获得更细腻的触感。

**必须保持**：所有新增动效都要在 `prefers-reduced-motion: reduce` 下正确降级
（`index.css` 已有全局兜底，新增动效只要用 CSS 类即可自动继承）。

### P1-3 首屏主包 378KB：PouchDB 未做懒加载

**证据**：

```
dist/assets/index-CGo6sJ3q.js       378 KB  ← 主入口
dist/assets/StatsPage-CK4gF2_1.js   386 KB  ← recharts
dist/assets/CalendarPage-D1qvyi3U.js 374 KB  ← lunar-javascript
```

主入口 378KB 的主因：`App.tsx` 静态引入了同步模块

```tsx
import { autoStartConfiguredSync } from './couchSync'
//  → couchSync.ts: import PouchDB from 'pouchdb-browser'
//    → localData.ts: import PouchDB from 'pouchdb-browser'（+ pouchdb-find）
```

而 `autoStartConfiguredSync` 只在挂载时调用一次，绝大多数用户**根本不用 CouchDB 同步**。

**建议**：改为动态导入，零风险立竿见影：

```tsx
// App.tsx
useEffect(() => {
  if (localStorage.getItem('ittime_sync_enabled') !== '1') return
  void import('./couchSync').then(m => m.autoStartConfiguredSync())
}, [])
```

预期主入口可减 100–150KB，首屏显著变快。

### P2-5 `transition-all` 触发不必要的重排

9 处 `transition-all`，其中 TimerPage 的搜索框用它做宽度动画：

```tsx

```

`transition-all` 会把 `width` 纳入过渡，导致**每帧触发 layout 重排**。
在低端 Android WebView（项目通过 Capacitor 支持移动端）上会掉帧。

**建议**：宽度动画改用 `transform: scaleX()` 或直接用 CSS Grid/容器查询，

显式列出 `transition-colors` / `transition-shadow` / `transition-transform`。

## 架构层面的整体判断

### 做得好的地方（应保留）

1. **域色系统架构正确** — `Layout.tsx` 单点注入 `data-domain`，
   三层架构（L1 原始色板 → L2 域指针 → L3 角色变量）清晰，
   亮暗双主题分流严谨（暗色下 `--d-solid` 改用 400 档配近黑字，这个决策很专业）
2. **路由级代码分割已做** — 9 个页面全部 `lazy()` 引入
3. **工程化校验脚本** — `scripts/design-tokens.mjs`（OKLCH 感知均匀校准）
   与 `scripts/verify-domains.cjs`（构建后域色回归），
   这套"设计即代码 + 自动校验"的思路是对的
4. **错误/空态三件套成熟** — `StateViews.tsx` 的伪元素扩热区、
   live region 分工（不重复播报）都考虑得很细
5. **无障碍基础扎实** — 全局 `:focus-visible`、`prefers-reduced-motion` 兜底
   （含 `.animate-spin` 反压细节）、`sr-only` 常驻 live region 都已到位

### 核心问题

**"设计系统文档"与"设计系统落地"之间存在断层——但断层的性质需要分清。**

4518 行设计文档里，`MOTION_SPEC` 的 L0–L4 五层动效在代码里落地有限，
`TOKENS_PLAN` 的中性色完全没有对应实现。

但实测表明，**这两类断层的视觉后果完全不同**：

- **动效断层 → 真实缺陷**（弹窗无退场 6ms、图表无入场）→ 需要补实现
- **中性色断层 → 非缺陷**（C 值 0.003–0.030，肉眼不可辨，替换反而更差）→ 需要改文档

所以"断层"本身不是问题，**把断层当缺陷来修才是问题**。
这提示了一个工程原则：设计系统的"定义"与"使用"不必强行对齐，
只有当落差产生**可感知的视觉或交互后果**时，才值得投入迁移。

### 一个此前未记录的架构事实（实测发现）

**Web 端是 local-first，服务端数据对页面不可见。**

`api.ts:234` 的 `req()` 把 `/categories|/tags|/todos|/timer|/goals|/memos|/plans`
全部交给 `localData.localRequest()` 走浏览器 IndexedDB（PouchDB `ittime-v1`）。
评审专家实测 `performance.getEntriesByType('resource')` 确认：页面只请求了
`/api/auth/status` 与 `/api/auth/session`，**从未请求 `/api/tags`**。

**这不是 bug，是有意的架构决策**（侧栏常驻的「本机即时保存 · 数据优先保留在当前设备」
正说明这点）。但它有两个实际后果：

1. **多端同步只存在于 CouchDB 手动同步路径上**，服务端 SQLite 不参与 Web 端渲染
2. **任何人以为"往服务端灌数据就能看到"都会踩坑**——包括本次审查最初的数据准备

如果这不是刻意的产品决策，建议在文档或设置页明确边界；
如果希望服务端也参与渲染，则需要补一条可选的服务端拉取路径。

**根治建议**：把 `verify-domains.cjs` 扩展成 `verify-design-system.cjs`，
增加以下断言并在 `npm run build` 后自动执行：

```
✗ 代码中不得出现裸 gray-* / slate-*（应走 n-*）
✗ rounded-lg / rounded-xl 不得用于卡片/面板（应走 rounded-card / rounded-panel）
✗ 字号不得低于 12px（禁止 text-[0.6rem] 以下的任意值）
✗ 声明了但零使用的动效类（提示未落地或已废弃）
```

这比任何一次性的代码替换都更有价值——它让断层不再复发。
