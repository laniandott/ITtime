## 零、总体结论

**这一轮质量明显提升。上一轮的三条 P0 全部修对了，而且修法是对的——不是打补丁，是把模型改对了。**

具体来说：状态拆成 `disposition` / `executionStatus` 双字段、推迟改为单向 `deferredFromId` + 反向派生、接管明确不继承 `planId`、`plannedMs` 补上并集、同日重叠直接禁止。这几处都不是敷衍修改，是把上一轮指出的**根因**处理掉了。

本轮**新发现 4 个问题**，其中 1 个是会让"一键开始"直接不可用的文档错误，1 个是架构层面的不变量无法保证。另有 6 处次要问题。

**结论：可以进入实现，但下面 P0/P1 要先处理。**

## 二、新发现的问题

### 2.1 【P0】§5.1 的 `store.start` 调用签名是错的，会让"一键开始"不可用

§5.1 写：

```
用户点计划块"开始"
  → store.start(block.tagId, block.note, block.todoId, block.id)
```

但现有签名（`apps/web/src/store.ts:17`）是：

```ts
start: (tagId: string, note?: string, todoId?: string, interruptedFromId?: string) => Promise<void>
```

**第 4 个位置参数是 `interruptedFromId`，不是 `planId`。** 照抄这段代码，`block.id` 会被当成 `interruptedFromId` 传下去。

后果分两种情况，都不好：

1. **现在**：本地路径（`localData.ts:185`）对 `interruptedFromId` **不做任何校验**，会静默写入 `interruptedFromId = <计划块 id>`。这个 id 指向的是一个 plan 文档而非 timer 文档。后续 `terminate-chain`（`localData.ts:215`）会沿 `interruptedFromId` 回溯，`get('timer', <planId>)` 直接 404。同时 `planId` 为空，靠 §2.4 规则 2 的标签重叠兜底才勉强能算，属于"看起来能用但数据是坏的"。
2. **按本轮新规则实现后**：§2.2 要求"本地路径和服务端路径都必须校验……`interruptedFromId` 的待续状态"。校验一上线，这个调用会**直接抛错**——一键开始彻底不可用。

`§3.4` 只说了"`start()` 增加 `planId` 参数并透传"，**没有指定参数位置**，而 §5.1 的示例又恰好填在了冲突的位置上。

**修正**：把 `start` 改成可选对象参数（`start({ tagId, note, todoId, planId, interruptedFromId })`），或在示例里显式写成 5 个位置参数。前者更好——现有 4 个位置参数已经很难读了，再加一个必然继续出错。同时 §9 应补一条"从计划块开始计时后，`TimeEntry.interruptedFromId` 必须为 null"的验收项。

### 2.2 【P1】§2.1 与 §3.5 关于目标的表述互相矛盾

三处口径不一：

| 位置 | 表述 |
|---|---|
| §2.1（L85） | "计划若通过 Todo 关联目标，则从 `todo.goalId` 推导" |
| §3.5（L229） | "**目标进度也不从计划块计算**，只从实际 TimeEntry 的标签计算" |
| §8 风险表 | "**计划不参与目标贡献计算**，Goal 只按实际 TimeEntry 标签统计" |

§3.5 和风险表是一致的，§2.1 那句是异类。它没说清楚"推导"出来的东西**用来干什么**——如果只是详情页显示"本计划服务于目标 X"，那没问题；如果参与进度计算，就和另外两处冲突。

**修正**：§2.1 改成明确限定，例如"仅用于详情页展示关联关系，不参与目标进度计算"，或直接删掉这句。

### 2.3 【P1】"同日不重叠"在本地优先架构下不是不变量

§2.4 规则 5：

> MVP 创建和编辑时**禁止**同一天的计划块互相重叠。这样每个实际时间片只有一个计划归属。

校验只发生在**本地写入时**。但这个系统的数据来源不止本地写入——还有 CouchDB 同步。

场景：设备 A 离线建了 9:00–10:00 编程，设备 B 离线建了 9:30–10:30 开会，两块各自都不与本地已有块冲突。同步后，**同一天出现了重叠的计划块**。

CouchDB 的复制不做业务校验，`resolveConflicts` 只做字段级合并（`localData.ts:71`），它不认识"同日不重叠"这个约束。所以：

- 这个"禁止"实际上只是**尽力而为的写入校验**，不是数据不变量；
- 而 §2.4 规则 5 的理由——"这样每个实际时间片只有一个计划归属"——**依赖**这个前提成立。前提被同步打破后，归属就退回到未定义状态，而文档没有定义这种情况。

**修正**：明确"重叠只保证在单设备写入时被拒绝；同步可能引入重叠"。然后定义同步后出现重叠时的行为（建议：两块都正常显示，不报错，单块覆盖率按 §2.4 规则 3 各自计算并在 UI 上标注"与另一计划重叠"）。不要把它当成不可能发生。

### 2.4 【P1】`api.ts` 清单漏了 `defer`

§3.1 要求新增接口：

> 新增 `POST /plans/:id/defer` —— 在一次本地写入流程中校验原块、检查同日重叠并创建带 `deferredFromId` 的后继块

但 §3.3 的 `api.plans` 对象里只有 `list / create / update / remove / skip / unskip`——**没有 `defer`**。

实施时按 §3.3 照抄，推迟功能就没有调用入口。

### 2.5 【P2】一级/二级标签精确匹配的后果没有提示

§2.4 规则 2 明确："仅在 `tagId` 精确相同且时间窗口重叠时作为候选。MVP 不把一级标签和二级标签自动视为相同标签。"

规则本身可辩护（与现有目标统计的精确匹配口径一致），但**后果没有写出来**，而这是个用户必然踩到的陷阱：

- 计划排在一级标签「编程」上
- 实际计时打在二级标签「编程 / 重构」上（因为二级标签才是可挂目标、可计时的具体活动）
- → 标签不精确相同 → 该计划**永远匹配不到任何实际记录** → `executionStatus` 恒为 `missed`

文档只给了规则，没给规避手段。

**修正**：补一句实现约束——计划块的标签选择器应默认只列"可直接计时"的标签，或在用户选择带子标签的一级标签时给出提示。

### 2.6 【P2】`deferred` 反向派生是 O(N²)，且删除后继块会丢失推迟历史

两个小问题：

**a. 复杂度。** §3.1 让 `joined('plans')` 派生 `disposition`，而判定 `deferred` 要扫描全部计划块找 `deferredFromId === this.id`；`list()` 对每个值都调 `joined`。一个月约 300 块就是约 9 万次比较。文档在风险表里专门担心 `list('timer')` 的全表扫描，却没对这里做同样的推理——口径不一致。

**b. 删除后继块会静默回退。** 原块的 `deferred` 完全靠"存在后继块"派生。若后继块被删除（用户改主意删掉了推迟后的新安排），原块**悄悄变回 `planned`**，推迟这件事没有任何痕迹——因为 `deferredAt` 在本轮被删掉了。需要明确这是否是期望行为。

### 2.7 【P2】`missedCount` 是否包含 deferred 块，未定义

`disposition` 与 `executionStatus` 拆开之后是正交的。于是"用户主动推迟、且当天零执行"的块：`disposition = deferred`、`executionStatus = missed`。

§3.5 的 `missedCount` 没有说明是否排除 `disposition === 'deferred'` 的块。用户**主动**推迟的安排被计入"未执行"，会让这个指标失真。

## 三、次要问题

### 3.1 续接链规则有重复条目

§2.2 的列表里：

- L105：由 `resumedFromId` 续接的记录，**默认**继承原记录的 `planId` 和 `todoId`。
- L107：由 `resumedFromId` 续接的记录继承原记录的 `planId` 和 `todoId`；这是执行来源追溯，不取代时间窗口重叠算法。

两条内容重复。而且 L105 的"**默认**"二字没有对应的例外条款——是上一版"默认继承、可被改写"的残留。现在既没有改写入口，"默认"就是误导。

**修正**：删掉 L105，保留 L107。

### 3.2 §4.3 与 §4.6 不一致

- §4.3：复用 `CalendarPage` 现有周 / 4 天视图，**不新增"计划"视图类型**
- §4.6：仍列出 `WeekPlanGrid.tsx`——周计划网格（挂进 CalendarPage）

如果不新增视图类型，这个组件的定位需要重新说明（是图层组件而非网格容器），否则实施时会照着一个不存在的"周计划视图"去建。

### 3.3 验收标准缺两类条目

新增的验收条目质量不错，但漏了两个正好对应本轮新机制的：

- **多设备并发推迟**：§2.3 提出"必须幂等"，但没有对应验收项。建议加"两台设备同时推迟同一原块，同步后不产生重复后继块"。
- **同步引入重叠**：对应 §2.3 的分析，建议加"同步后出现重叠计划块时，界面不报错且两块覆盖率各自可解释"。

## 四、流程层面

### 4.1 排期建议反转了，但没说为什么

§7.3 现在是：

> 先完成阶段一的待续栈和活动链验收，再在阶段二的数据与同步基础上接入本地计划实体；计划与实际的独立指标属于阶段三的可解释洞察。

这**反转**了此前的建议（"纯加法，可作为阶段一验收期间的并行项"）。新写法更贴合 v0.4 自身的排期原则，方向上是更保守、更稳的。

但有两个问题：

1. **没有说明为何反转**。读者无法判断这是重新论证的结论还是随手改的。
2. **它把你现在就需要的功能推迟了**。你的原始动机是"我现在就需要一个计划表来约束自己"，而按这个排期，计划功能要等 v0.4 阶段一验收完、再在阶段二接入。这是一个**需要你拍板的取舍**，不该由文档单方面决定。

### 4.2 `plan-integration-summary.md` 仍然没修

本设计文档已不再自称权威（改对了），但**错误的那一方依然没人去改**：

- `plan-integration-summary.md` §3 仍写着"计划块允许 **30 分钟到数小时**的弹性时长"
- 本设计文档写"精确到分钟"

仓库里依然是两份互相矛盾的设计文档。本轮把裁决权从设计文档里拿掉了，但**冲突本身没有消除**。

**修正**：直接改 `summary` §3，或在那里加一条指向本设计文档的作废批注。

## 六、一句话总结

**上一轮的根因问题全部修对了，这一轮的模型是站得住的。** 剩下的是一个会卡住"一键开始"的调用签名错误（P0）、一处目标口径自相矛盾、以及一个被当成硬规则但架构上保证不了的"同日不重叠"。

前两条改完就能开工；第三条需要在实现时按"同步可能引入重叠"来写防御逻辑，而不是假设它不会发生。
