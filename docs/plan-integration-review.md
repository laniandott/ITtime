# 审核报告：`plan-integration-summary.md`

**审核对象**：`docs/plan-integration-summary.md`（ITtime 计划模块融合方案）
**审核基准**：`功能演进计划 v0.4.md`、当前代码 `0e1fef2`（`laniandott/ITtime` = 本地 `F:/projects/ITtime-tagtime`）
**审核日期**：2026-10-15

---

## 总体结论

**这是一份合格的"产品愿景说明"，但不是一份可施工的实施方案。**

它的概念边界意识是对的——"显示可以融合，数据语义不能混淆"这个原则抓得准，与 v0.4 不变规则 6 同向。但它最大的问题不是**写错了什么**，而是**没写**：ITtime 的本地优先同步架构、待续栈机制、v0.4 不变规则这三块地基，是决定计划模块长什么样的前提，文档一块都没碰。同时它在时间粒度上与你已确认的决策相反。

按施工图标准衡量，**不建议直接照着它开工**。

---

## 一、与已确认决策冲突（必须最先修正）

### 1.1 时间粒度写反了

文档 §3：

> 计划采用"时间块"模型，而不是把每天强行切成完整的小时表。
> 计划块允许 **30 分钟到数小时**的弹性时长。

这与你明确确认的"**精确到分钟**"直接冲突，也偏离了你的原始动机——你要的就是"像记事本那样的按时计划模板"。

具体后果：30 分钟下限会让"15 分钟快速处理邮件"这类计划**无法创建**。

**更关键的是**：文档对分钟级粒度真正的难点一个字没提——1440px 时间轴在小屏上怎么点选、拖拽吸附多少分钟、短于 15 分钟的块怎么渲染。这恰恰是这个方案里唯一需要动脑的交互问题。

### 1.2 全文没有出现你的原始诉求

你原话是"每日每小时的计划项目"。文档通篇在论证"不要切成小时表"，实际上是在反对需求本身。如果这是有意的产品建议，应当**明确说明理由并请求确认**，而不是静默地改变需求。

## 二、缺失地基（最致命）

### 2.1 完全没有提"本地优先 + CouchDB 同步"架构

这是 ITtime 当前最大的技术现实：核心实体（`categories` / `tags` / `todos` / `timer` / `goals` / `memos`）存在浏览器 PouchDB，经 CouchDB 跨设备同步；服务端 SQLite 只保留日历、笔记、上传。

文档通篇没有回答"`PlanBlock` 存在哪里"。这不是细节，**这是决定整个实现形态的第一个问题**：存本地还是存服务端，决定了 API 形态、离线行为、冲突处理方式，三条路线完全不同。

### 2.2 缺具体接入点

如果要落进现有代码，至少涉及三处，文档都没提：

| 接入点 | 风险 |
|---|---|
| `apps/web/src/localData.ts` 的 `isLocalPath` 正则 | 不加 `plans`，请求会走服务端而非本地 |
| `localData.ts` `write()` 的字段剥离列表 | 派生字段会落库，污染文档 |
| `couchSync.ts` `countSyncDocuments` 的实体集合 | **漏加 `plans` 会让设置页同步文档计数对不上**，与 `MIGRATION_STATUS.md` 中"设置页显示的文档数量要能解释"的要求冲突 |

### 2.3 没提"计划不得进入时长统计"

v0.4 不变规则 6 写明"删除、同步和恢复不能让统计悄悄改变语义"。文档 §5 只说"实际专注时长"要展示，却从未声明计划块**不得**被现有 `elapsed()` / `StatsPage` 时长统计读取。缺了这条隔离约束，实现时极容易把计划时长混进"今日时长"，直接摧毁这个数字的可信度。

### 2.4 没提 v0.4 的既有约束

文档未引用 v0.4 的 7 条不变规则、暂缓事项，也没交代本方案与 v0.4 阶段划分的关系。其中 §4 的日历图层方案与 v0.4 §5.2 的既有规定**直接打架**（见 4.2）。

## 三、数据模型问题

### 3.1 `status` 把"派生结果"和"用户意图"混在一个字段里

文档 §8 存 5 个状态：计划中 / 进行中 / 已完成 / 已跳过 / 已推迟。

问题在于：

- **进行中 / 已完成** ← 应从 `TimeEntry` **派生**
- **已跳过 / 已推迟** ← 是**用户显式意图**

两类语义塞进一个可写字段，后果有两个：多设备并发编辑必然冲突（`fieldClock` 字段级合并救不了"同一个字段同时被派生逻辑和用户操作修改"）；状态可能与实际记录不一致——而 v0.4 规则 6 要防的正是这个。

**建议**：拆成"存储用户意图（`skippedAt` / `deferredTo`）+ 派生执行结果"。

### 3.2 "已推迟"是个语义黑洞

推迟到**什么时候**？没有目标时间字段。没有目标的"推迟"无法在界面上重新落位，也无法计算达成率——它只是一个把块变灰的开关。

### 3.3 `goalId` 与 `tagId` 冗余且可能矛盾

文档 §8 让 `PlanBlock` 同时挂 `tagId` 和 `goalId`。但代码里 `Goal.tagId` 是**必填**（`apps/server/src/schema.prisma`，`tagId String` 非可选）。

于是：当计划的 `tagId` 与该 `goalId` 所属的标签**不是同一个**时，这条计划算哪个目标的贡献？规则未定义，且没有校验。

**建议**：要么去掉 `goalId`（由 `tagId` 反查目标），要么强制 `goalId.tagId === tagId` 并写校验。

### 3.4 `date` 字段类型未定义

是字符串还是 `Date`？时区按哪个算？"按天查计划"是本功能最核心的查询，这个字段的类型必须先钉死。

（建议：`YYYY-MM-DD` 本地日历日 + 分钟数偏移，而非 ISO 时间戳——计划是"墙上时钟"语义，用时间戳会引入跨时区设备上"计划跳到前一天"的 bug。）

### 3.5 `planBlockId` 没处理续接链

ITtime 有 `resumedFromId` 续接链：计划块执行中被暂停，续接后会产生**新的** `TimeEntry`。

文档没说续接产生的 entry 要不要继承 `planBlockId`。不继承的后果很直接：**一个计划块只关联到半截执行**，"计划 vs 实际"对照计算直接算错。这是 ITtime 特有的坑。

### 3.6 关联模型选错了方向

文档 §8 选择"`TimeEntry.planBlockId`（1 计划 → N 计时）"，并说"若未来需要一个计时跨越多个计划块，再升级为多对多关联表"。

但真实场景里，**反向**的跨越更常见：你计划 9:00–10:00 编程、10:00–11:00 编程两个块，实际却只按了一次计时器跑 9:00–11:00。这种情况下，**第二个计划块拿不到任何归属**，会被误判为"未执行"。

**建议**：对照计算改用**时间窗口重叠**（entry 与 plan block 的时间区间求交），而不是依赖外键。外键只用于"从计划块启动计时"这个动作。

### 3.7 缺基础约定

未定义主键生成策略、文档 ID 格式、软删除（`deletedAt` + tombstone）语义、以及计划块被删除后已关联 entry 的孤儿处理。

## 四、与现有机制脱节

### 4.1 完全没提"待续栈"——最大的认知盲区

ITtime 阶段一（当前 P0）的核心机制就是**暂停 → 待续 → 续接 / 算了**，含 `pendingResume`、`resumedFromId`、`interruptedFromId`、`terminate-chain` 一整套。

文档 §5 列出要展示"**中断次数**"这个指标，但从未说明数据从哪来——正是这套机制。更没回答：计划块执行中被暂停时，待续栈里应该显示什么？"算了"之后计划块变成什么状态？

这是 ITtime 区别于所有普通待办 App 的独特能力，计划模块如果不接上去，等于把最值钱的机制浪费了。

### 4.2 日历图层方案与 v0.4 既有规定冲突

文档 §4 提议"5 个可切换图层"（外部事件 / 计划块 / 实际计时 / Todo 截止 / Memo 标记）。

但 v0.4 §5.2 已明确规定：

> 视图切换只保留月、周、4 天。
> 月视图只显示活动、记录和外部日历的色点，**不显示"1 条记录"或时长文字**。

加 5 个可切换图层是明显的范围膨胀，且与既定的"月视图保持简洁"规则打架。要么明确说明这是对 v0.4 的修订，要么收缩方案。

### 4.3 "今日"页面的导航代价没算

文档 §9 说"'今日'应成为计划功能最主要的执行入口"，并列出一个 6 页结构。

但事实是：底部导航**已经有 6 项**（打卡 / 待办 / 习惯 / 统计 / 日历 / 设置），而"打卡"页本身就是执行入口。所以 §9 实际上只是把现状重述了一遍，同时**悄悄引入了一个新页面**，却没说是新建第 7 个 tab（移动端触控区会被挤压），还是改造"打卡"页。

### 4.4 "手动标记完成"会瓦解达成率

§10 阶段一要求"支持……完成、跳过和推迟"，即允许用户**手动**把计划块标为完成。

但 §5 又说"计划完成不能直接等同于打卡完成"，§11 规则 4 也强调这一点。如果用户可以随手把计划标成"已完成"，那么达成率就退化成**自报数据**，指标失去意义。

需要明确：手动"完成"到底意味着什么？建议区分"计划已处理"（用户关掉这个块）与"实际达成"（由计时覆盖率派生），两者分开显示。

## 五、方案结构问题

### 5.1 阶段划分自相矛盾

- **阶段一**要求"允许从计划块启动计时"
- **阶段二**才要求"计划和 TimeEntry 建立关联"

没有关联，阶段一的"启动计时"就无法把实际记录回指到计划块——启动之后就是一个普通计时，计划块永远停留在"进行中"。**阶段一和阶段二的内容是互斥的。**

### 5.2 阶段一颗粒度过大

阶段一一次交付：数据模型 + CRUD + 今日时间轴 + 创建/编辑/移动/完成/跳过/推迟 + 关联 Todo/Tag + 启动计时。

这是一个完整子系统，中途无法验证，出问题时也定位不到是哪一层。建议按"数据层 → 只读时间轴 → 创建编辑 → 一键开始 → 对照"切成可独立验证的小步。

### 5.3 没交代与 v0.4 排期的关系

v0.4 写明"只有阶段一和阶段二稳定后才进入本阶段"。文档提出一个 4 阶段的独立路线，却没有说明：是与 v0.4 的阶段并行、替换、还是插队？两个路线图并存会造成执行混乱（这正是 `FEATURE_ROADMAP.md` 与 `功能演进计划 v0.4.md` 已经发生过的问题）。

### 5.4 缺交付标准

没有验收标准、没有测试计划、没有风险表、没有依赖顺序。作为实施方案，这三样是硬通货。

### 5.5 文档定位混乱

标题说"产品定位、模块关系和长期融合方案"（愿景），正文却给了"建议的数据关系"和"分阶段实现路线"（施工）。两种性质混在一起，读者不知道该当愿景读还是当施工图用。

**建议拆分**：愿景归愿景（可保留本文档主体），实施另出一份，明确"数据存哪、怎么同步、接入哪些文件、怎么验收"。

## 六、值得肯定的部分

审慎起见也要说清楚哪些是对的，避免误伤：

1. **§2 的核心原则正确**——"显示可以融合，数据语义不能混淆"，与 v0.4 规则 6 同向，是本方案最有价值的判断。
2. **§5 边界抓得准**——"计划完成不能直接等同于打卡完成"，并区分时长型目标（按实际计入）与次数型目标（按打卡计入），这段逻辑是对的。
3. **§6 多计划块对应一个 Todo**——正确，且与 v0.4 规则 2 一致。
4. **§8 明确"计划不应存成 Todo 的 dueDate"**——关键判断，避免了最容易被误踩的坑。
5. **§4 "初期只读外部日历，不写回"**——克制且正确。
6. **§11 的 7 条产品规则方向正确**，可作为后续文档的骨架。
7. **§7 的 `PlanBlock -> TimeEntry -> Memo` 复用路径**——比新建 `PlanBlock -> Memo` 优先，顺序合理。
