## 一、必须回退或修正的硬伤

### 1.1 【严重】接管记录继承 `planId` 是错的

新增的"续接链规则"第二条：

> 由 `interruptedFromId` 接管的记录，也默认继承原记录的 `planId`；只有用户明确选择其他计划时才改写。

**这条是错的，且与代码自身的语义约束直接冲突。**

代码证据（`apps/server/src/routes/timer.ts`）：

| 字段 | 代码约束 | 语义 |
|---|---|---|
| `resumedFromId` | `if (parentEntry.tagId !== tagId) return 400 '续接的 tagId 必须与原记录一致'`（L166-168） | **同一活动**的继续 |
| `interruptedFromId` | 只校验"被接管的活动必须处于待续状态"（L187-189），**不校验 tag** | **不同活动**的接管 |
| 两者 | `if (resumedFromId && interruptedFromId) return 400 '续接和接管不能同时指定'`（L151-153） | 互斥 |

`interruptedFromId` 的完整业务含义是：**有序活动暂停后，用户从"选择接下来做什么"弹窗里挑了另一个活动**（`TimerPage.tsx:636`、`L2028` 标题即"选择接下来做什么"）。被接管的那个活动**必然是另一个标签**——这正是它与"续接"的区别。

**因此，让接管记录继承原记录的 `planId` 会直接算错对照。**

反例（真实路径）：

```
计划块 P：9:00–10:00 编程
09:00  从 P 开始计时（entry.planId = P）
09:05  暂停（有序活动 → 弹"选择接下来做什么"）
09:05  选择"开会" → 新 entry 带 interruptedFromId，tag = 开会
```

按这条新规则，开会那条 entry 会继承 `planId = P`。于是 §2.4 的对照算法把 09:05 之后的开会时间**全部计入"编程计划块 P 的实际覆盖"**——P 显示 100% 达成，而实际上编程只发生了 5 分钟。

这不是边界情况，而是 ITtime 阶段一主流程的**正常路径**（暂停→选下一活动→接管）。

**修正**：接管记录**不得**继承 `planId`。只保留 `resumedFromId` 的继承。另外"用户明确选择其他计划时才改写"这句也要删——代码里没有任何"接管时选择计划"的入口，这是凭空的机制。

### 1.2 【严重】`deferredToId` + `deferredFromId` 双向指针破坏写入原子性

新增字段：

```ts
deferredToId: string | null    // 推迟后生成的新计划块
deferredFromId: string | null  // 新计划块指向原计划块
```

推迟一次要写**两个文档**：更新原块（写 `deferredAt` + `deferredToId`）并新建后继块（写 `deferredFromId`）。这是跨文档的两次独立写入。

在 PouchDB + CouchDB 架构下这不成立：

1. **没有跨文档事务**。`localData.ts` 只用 `navigator.locks` 串行化单次 `localRequest`，两次 `db.put` 之间没有任何原子保证。
2. **失败即悬空**。若第二次写入失败（离线、崩溃、关标签页），原块的 `deferredToId` 指向一个**不存在的块**。派生状态永久停在 `deferred`，而"推迟到的新时间"从未存在——原计划从当天执行视图里彻底消失，且没有任何报错。
3. **同步放大**。CouchDB 按文档独立复制，对端可能先收到改过的原块、后收到新块（或永远收不到），产生跨设备的不一致窗口。
4. **合并逻辑不认业务**。`resolveConflicts` 是字段级合并，它不知道"这两个字段必须成对出现"。两个设备各推迟一次，合并结果可能是"原块指向 A、A 指向另一个源"，指针互相打架。

**修正**：只保留**单向**指针。推荐只在新块存 `deferredFromId`，原块的"已推迟"状态用反向查询（`blocks.filter(b => b.deferredFromId === this.id)`）派生。这样推迟只写一次新文档，原子、无悬空、合并安全。一天的计划块数量很小，反向扫描没有性能问题。

### 1.3 【中等】`plannedMs` 没做并集去重，与 `actualMs` 口径不对称

§2.4 规则 4 只说：

> 总体 `actualMs` 和 `unplannedMs` 也使用区间并集，避免重叠计划块把同一段实际时间算两遍。

**但 `plannedMs` 没提。** 而 §2.4 规则 5 又明确允许两个计划块互相重叠。

于是：`actualMs` 去重了，`plannedMs` 还是 `Σ(endMinute - startMinute)` 的朴素求和（重叠部分被算两遍）。初稿定义的 `adherenceRate = actualMs / plannedMs` 就变成**分子去重、分母不去重**——达成率被系统性低估。

举例：计划 9:00–10:00 编程、9:30–10:30 编程（重叠 30 分钟），实际 9:00–10:30 编程 90 分钟。

- `actualMs`（并集）= 90 分钟
- `plannedMs`（朴素求和）= 60 + 60 = 120 分钟
- 达成率 = 75%，而真实达成率是 100%

**修正**：`plannedMs` 必须同样取计划窗口的区间并集。并明确写出口径：所有时长类指标一律"先取并集，再计算"。

### 1.4 【中等】重叠计划块的归属问题被回避了

§2.4 规则 5：

> 若两个计划块互相重叠，按显式 `planId` 优先、再按开始时间排序进行展示；统计仍以并集为准。

这句只解决了**展示顺序**，没解决**归属**。

后果：两个重叠块各自单独看覆盖率时，同一段实际时间会被**同时**计入两块。于是两块都显示"100% 达成"，而用户只干了一遍。单块达成率在重叠场景下失去意义。

要么禁止重叠（创建时校验并提示），要么定义明确的归属规则（如"显式 `planId` 优先，其余按开始时间先到先得，不重复分配"）。"统计以并集为准"只对总量指标有效，对单块指标无效——文档把两者混为一谈了。

## 二、仍然没有闭合的问题

### 2.1 §2.2 的理由与 §2.4 的算法自相矛盾

§2.2 说：

> 续接链中的每一段都保留自己的 `planId`，不能只在链首记录计划，**否则暂停后的实际时间会从计划对照中消失**。

**这个理由是错的。** 按 §2.4 规则 2，"没有 `planId` 的记录，在标签相同且时间窗口重叠时也作为候选"——续接记录的标签**必然**与原记录相同（代码 L166-168 强制），所以即使不继承 `planId`，规则 2 也会把它捞回来。

反过来，如果续接时段已经跑到计划窗口之外（9:00 的计划，14:00 才续接），那么继承 `planId` 也救不了——规则 3 取的是与计划窗口的**交集**，交集为空，照样是 0。

所以两个分支下这句理由都不成立。继承 `planId` 本身是好事（用于追溯来源），但**不能拿"否则会消失"当理由**，因为实际兜底的是规则 2。文档需要说清两者的分工，否则实现者会以为继承是必需的、进而写出重复归属的逻辑。

### 2.2 【关联发现】本地路径没有校验续接的标签一致性

代码里 `resumedFromId` 的"标签必须一致"只在**服务端**校验（`timer.ts:166`）。**本地路径没有这个校验**（`localData.ts:186`）：

```ts
if (body.resumedFromId) {
  const previous = await get(entity, body.resumedFromId)
  if (!previous.pendingResume) throw new Error('原记录不在待续状态')
  await write(entity, { ...previous, pendingResume: false })
}
```

只查 `pendingResume`，不查 `tagId`。

目前靠 UI 兜住了（`store.resumeEntry` 传的是 `pendingEntry.tagId`，所以实际不会不一致），属于**潜在缺陷**。但本设计文档的"续接链规则"要建立在这个不变量之上，就必须先把这个校验补到本地路径，否则规则的前提在本地是不成立的。

### 2.3 `status` 派生优先级未定义

派生表新增了 `deferredToId` 非空 → `deferred`，但没写**优先级**。

当 `skippedAt` 与 `deferredToId` **同时非空**时（用户先推迟、又决定原块不做了），算哪个？表里 `skippedAt` 在上，暗示 skipped 优先，但没有任何一句话说明。派生表必须显式声明判定顺序。

### 2.4 `deferred` 短路导致部分执行信息丢失

`deferredToId` 非空就短路成 `deferred`，跳过了后面的覆盖率判定。

于是"推迟了但当天还是做了一部分"这种情况，`status` 只剩 `deferred`，**看不出已经投入过时间**。文档说这样设计是为了"复盘时能区分'原本安排但推迟'和'新时间实际安排'"——但 `status` 是**单值**字段，它区分不了"推迟且零执行"和"推迟但做了一半"。

`actualMs` 还在，信息没彻底丢，但**界面上不能只依赖 `status`**。这一点需要显式写进文档，否则实现者会直接拿 `status` 渲染，把"推迟但做了一半"画成一片空白。

### 2.5 `goalId` 的矛盾只是转移，没有解决

新增段落说：

> v0.1 不直接保存 `goalId`。`Goal.tagId` 是必填字段，计划若通过 Todo 关联目标，则从 `todo.goalId` 推导……未来若增加直接关联目标，必须校验 `goal.tagId === plan.tagId`

问题在于：**`Todo.goalId` 指向的 Goal，其 `tagId` 同样可能与 `plan.tagId` 不一致。**

```
计划块：tagId = 编程
  └─ todoId → Todo"完成季度报告"（tagId = 写作）
                └─ goalId → Goal（tagId = 写作）
```

这条计划到底算"编程"还是"写作"的贡献？文档没说。原初稿的 `goalId`/`tagId` 矛盾被原样搬到了 `todo.goalId` 这一层，还多绕了一层。

**修正**：要么对 `todo.goalId` 的路径也加同一条校验（`goal.tagId === plan.tagId`，不一致则不推导），要么干脆规定"计划块不参与目标贡献计算，目标只按实际 `TimeEntry` 的标签统计"——后者更干净，也和 §2.4 的对照算法同源。

### 2.6 "标签相同"是否包含父子层级，未定义

规则 2 依赖"标签相同"。但 ITtime 的 `Tag` 有 `parentId` 父子层级（`schema.prisma`），一级标签可直接计时、二级标签可挂目标和待办。

那么：计划块挂在一级标签"编程"下，实际计时打在二级标签"编程/重构"上——算不算"标签相同"？

现有代码里，目标统计用的是**精确匹配**（`localData.ts` 的 `entry.tagId === value.tagId`）。如果这里也精确匹配，那么"一级标签上的计划"将永远匹配不到"二级标签上的实际计时"，对照恒为 0。这是个会真实踩到的坑，文档必须明确写出匹配规则。

### 2.7 待续栈交互仍然没写

上一轮审核列出的 P1 项——"计划块执行中被暂停（`pendingResume`）时，计划块是什么状态？待续栈里显示什么？'算了'之后计划块变成什么？"——本次修订**仍未回答**。

新的"续接链规则"只覆盖了 `TimeEntry` 层的 `planId` 继承，没有覆盖**待续状态**与计划块的关系。这是 ITtime 阶段一的核心机制，不能靠"继承 planId"一句话带过。

## 三、流程与文档层面的问题

### 3.1 只改了一份文档，两份文档现在公开矛盾

`plan-integration-summary.md` **一个字没动**（仍是 09:04、8536 字节），它 §3 依然写着：

> 计划块允许 **30 分钟到数小时**的弹性时长

而本设计文档写着"精确到分钟"。两份文档现在**直接对立**。

GPT 的处理方式是在本设计文档开头加了一句：

> 两者冲突时，以本文档和 `功能演进计划 v0.4.md` 的既有规则为准。

这个处理有三个问题：

1. **单方面宣布**。把裁决权写进其中一方，而不是去修正错误的那一方。正确做法是修 `summary` 的 §3，或至少在那里加一条作废批注。
2. **覆盖范围过大**。"以本文档为准"是**全篇**优先。但 `summary` 里有若干本文档**没有复述**的产品原则（如"计划完成不能等同于打卡完成"、`PlanBlock -> TimeEntry -> Memo` 的复用顺序、图层分离原则）。全篇优先会让这些原则在实现时被当作已废止。
3. **裁决依据不成立**。它说以"本文档和 v0.4 的既有规则"为准——但两份文档在**粒度**上的冲突，v0.4 里根本没有相关规定，裁决依据是空的。

### 3.2 "权威施工稿"是自我加冕

本设计文档自身还是 v0.1 草案、未经用户确认，却在开头宣布自己是"实现时的权威施工稿"。两份草案之间不存在谁权威于谁——**权威只能来自用户确认**。这句话应当改成待确认状态，或干脆删掉，由用户在读过两份文档后指定。

### 3.3 修订记录没更新

文档末尾"修订记录"仍只有：

| v0.1 | 2026-10-15 | 初稿。确定独立实体、本地优先、分钟级粒度、双层界面 |

12:14 这次修订新增了 `deferred` 状态、续接链规则、对照算法三块内容，修订记录**一字未改**。设计文档的版本追溯断了，后续无法判断哪一版引入了什么决策。

### 3.4 验收标准与实施步骤没同步

新增了三个机制（推迟、续接链继承、区间并集对照），但：

- §9 验收标准**没有增加任何对应条目**
- §6 实施步骤**没有增加对应步骤**

新增的机制没有验收口径、没有实施路径。其中"接管不继承 planId"这条如果按 1.1 修正，恰恰是最需要写进验收标准的一条（因为它是个反直觉的约束，最容易被后续实现者改回去）。

## 五、一句话总结

**这次修订把两个方向性问题修对了（对照改用区间重叠、`goalId` 不再直接存），但顺手写错了一条会算错数据的规则（接管继承 `planId`），并且在"推迟"上引入了一个在 PouchDB 下不成立的跨文档写入。另外，新增的三个机制没有一条配了验收标准。**

建议：P0 三条改完后，再补验收标准和修订记录，然后才可以进入实现。
