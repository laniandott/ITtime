# ITtime 计划模块融合方案

## 1. 文档目的

本文档记录 ITtime「每日计划 / 时间块计划」的产品定位、模块关系和长期融合方案。

计划功能不是一个孤立的小时清单，也不应该替代待办、日历或计时。它应当成为 ITtime 的“执行层”，把“想做什么”转化为“准备什么时候做”，再和实际执行结果连接起来。

本文档面向 ITtime 整体项目。当前代码基线以功能较完整的 `ITtime-tagtime` 为主要参考，最终落地目录和主线需要项目维护时统一确认。

## 2. 核心概念边界

| 模块 | 主要回答的问题 | 数据语义 |
| --- | --- | --- |
| Todo | 我要做什么 | 待办事项和完成状态 |
| Calendar | 已经有什么固定安排 | 外部或固定事件 |
| Plan | 我准备什么时候做 | 可调整的计划时间块 |
| Timer / TimeEntry | 实际做了多久 | 真实活动记录 |
| Goal / Habit | 长期目标是否达成 | 周期性目标和进度 |
| Memo | 过程中发生了什么 | 备注、日记和复盘记录 |

设计原则：**显示可以融合，数据语义不能混淆。**

例如同一时间段可以同时显示外部会议、计划中的编码、实际计时和一条备忘录，但它们仍然是四种不同的数据。

## 3. 计划模块定位

计划采用“按分钟设置的时间块”模型，保留记事本式的明确时间安排，同时允许用户只安排真正需要管理的时段，不要求全天无缝排满。

一个计划块至少包含：

- 用户填写的具体计划内容，必填，可写多行
- 计划开始时间和结束时间
- 可选挂载 Tag，用于分类和与实际计时自动对照
- 可选关联 Todo
- 用户手动确认，可与客观计时结果分开显示

计划时间精确到分钟；界面可以用 5 分钟吸附提高操作效率，但不能把计划限制为 30 分钟或更大的粒度。计划内容和时间段由用户自己填写，Tag 不是计划内容，也不是创建计划时的必选入口。

计划是“准备执行的意图”，不是事实记录。只有计时、打卡或用户明确操作，才会产生实际完成结果。

## 4. 与日历的融合

计划应该在日历中显示，但不应该直接复用外部 `CalendarEvent` 数据模型。

日历页面建议提供多个可切换图层：

- 外部日历事件：会议、课程、预约等硬约束
- ITtime 计划块：用户安排的执行时间
- 实际计时记录：已经发生的活动
- Todo 截止时间：需要完成的期限
- Memo / 日记标记：该时间段的记录

外部日历事件通常是硬约束，计划是可移动的软安排。出现冲突时提示用户，但不必禁止创建计划。

初期建议只做外部日历的读取和展示，不直接写回 Google Calendar 等外部服务。后续可以提供单独的计划 ICS 导出，避免同步来源不清和重复事件问题。

## 5. 与计时和打卡的融合

从计划块开始计时，是计划和实际执行之间的主要连接方式。

建议的执行流程：

1. 用户先填写具体计划内容并设置时间段。
2. 可选挂载 Tag 和 Todo；Tag 只是分类/执行上下文，不是计划内容。
3. 到时间后点击“开始”，自动启动计时；未挂 Tag 时先补选 Tag，再开始。
4. 生成的 `TimeEntry` 关联该计划块。
5. 计时被暂停或中断时，可以产生多个实际时间片。
6. 结束计划时，用户可以推迟、跳过或手动确认；手动确认不等于客观计时完成。

计划内容完成不能直接等同于打卡完成，Tag 也只是可选的执行上下文：

- 时长型目标：计划 60 分钟，实际专注 36 分钟，则目标只计入实际 TimeEntry 的 36 分钟；计划本身不贡献目标进度。
- 次数型目标：只有实际完成打卡动作才增加次数。
- 计划经过但没有执行：记录为计划未执行，不自动伪造一次打卡。

计划和打卡的差异应该可查看，但不要用单一分数惩罚用户。至少应展示：

- 计划时长
- 实际专注时长
- 执行比例
- 实际开始与计划开始的偏差
- 中断次数
- 未执行或推迟原因

## 6. 与 Todo 的融合

Todo 表示任务本身，Plan 表示执行安排，两者应保持独立。

一个 Todo 可以对应多个计划块：

```text
Todo：完成季度报告
计划块 1：收集资料
计划块 2：撰写初稿
计划块 3：修改和提交
```

Todo 的截止时间表示“最晚什么时候完成”，计划的开始和结束时间表示“准备什么时候执行”。

完成一个计划块不应默认完成 Todo，因为一个 Todo 可能需要多个时间块。计划可以反映任务推进情况，但是否完成整个 Todo 应由用户明确确认或按明确的产品规则处理。

从 Todo 页面和计划页面都应支持快速创建关联对象：

- 从 Todo 排入某个时间段
- 从计划块创建一个新 Todo
- 从计划块启动关联 Todo 的计时
- 查看某个 Todo 的计划历史和实际投入

## 7. 与 Memo、日记和笔记的融合

计划块应支持执行后的快速记录，适合记录结果、阻塞原因和临时想法。

当前 ITtime 已经支持 `TimeEntry -> Memo`，因此第一阶段可以通过以下关系复用现有能力：

```text
PlanBlock -> TimeEntry -> Memo
```

后续再支持没有启动计时的计划直接关联 Memo：

```text
PlanBlock -> Memo
```

例如散步、休息、家庭事务可能不需要计时，但仍然值得记录。

晚间复盘应能同时查看：计划内容、实际计时、Todo 状态和相关 Memo。

笔记系统后续可以增加 `plan` 类型的实体链接，使长期笔记能够引用某个计划或某天的计划记录。

## 8. 建议的数据关系

第一阶段新增独立的 `PlanBlock` 实体：

```text
PlanBlock
- id
- date
- content
- plannedStart
- plannedEnd
- tagId，可选
- todoId，可选
- skippedAt，可选
- confirmedAt，可选
- deferredFromId，可选
```

实际计时记录可以先增加可选的 `planBlockId`：

```text
TimeEntry
- planBlockId，可选
```

这样可以支持一个计划块对应多段计时，适配暂停、打断和续接。若未来需要一个计时跨越多个计划块，再升级为独立的多对多关联表。

计划不应直接存成 Todo 的 `dueDate`，也不应直接存成外部 CalendarEvent。这样可以保留截止时间、计划时间和实际时间的区别。计划不直接贡献 Goal 进度，Goal 只根据实际 TimeEntry 的标签计算。

## 9. 页面和入口建议

ITtime 可以逐步形成以下页面结构：

- **计划**：独立的每日计划笔记工作区，按天显示 00:00–24:00 分钟时间轴
- **日历**：按日、周、月查看外部事件、计划和实际记录
- **打卡 / 计时**：执行活动并记录真实时间，可从计划笔记启动计时
- **待办**：管理任务池、优先级和截止时间
- **目标 / 习惯**：查看周期目标和达成情况
- **统计**：比较计划投入、实际投入和目标完成度

计划页是填写和调整计划笔记的主工作区；日历负责跨天查看，计时页负责记录实际活动，统计页负责对照计划与实际。计划内容按分钟落在每日时间轴上，Tag 仅作为可选分类。

## 10. 分阶段实现路线

### 阶段一：计划基础

- 新增 PlanBlock 数据模型和 CRUD
- 提供独立计划页的每日时间轴和计划笔记编辑器
- 支持创建、编辑、移动、跳过、推迟和手动确认；客观执行结果由实际计时派生
- 支持关联 Todo、Tag
- 允许从计划块启动计时

### 阶段二：统一日历和执行反馈

- 日历显示计划图层
- 计划和 TimeEntry 建立关联
- 显示计划时长与实际时长
- 增加冲突提示和拖动调整
- 支持计划块的执行结果和偏差原因

### 阶段三：目标、Memo 和复盘

- 展示计划关联 Todo 所对应的 Goal / Habit，但目标进度仍只来自实际 TimeEntry
- 计划结束后快速添加 Memo
- 每日复盘查看计划、实际、Todo 和 Memo
- 展示时长目标和次数目标的实际贡献

### 阶段四：重复计划和外部协作

- 工作日或星期重复计划模板
- 从模板生成每日计划
- 计划 ICS 导出
- 更完整的周计划和统计分析
- 笔记系统支持计划实体链接

## 11. 需要坚持的产品规则

1. 计划是执行意图，TimeEntry 是实际事实。
2. Todo 的截止时间和 Plan 的执行时间不能混为一谈。
3. 外部日历事件和内部计划可以统一显示，但生命周期分开管理。
4. 完成计划块不自动等于完成 Todo 或习惯打卡。
5. 实际数据应能解释计划偏差，而不是只显示一个简单的完成率。
6. 用户可以快速调整计划，计划系统不能因为一次延误就整体失效。
7. 计划块可以关联多个实际时间片，以适应暂停和中断。

## 12. 最终产品闭环

```text
Todo 待办池
  -> 安排到 Plan 时间块
  -> 到点启动 Timer / 打卡
  -> 产生 TimeEntry 和 Memo
  -> 推进 Todo 和 Goal
  -> 对比计划与实际
  -> 调整下一天的计划
```

最终目标不是让用户填写一张漂亮的时间表，而是让 ITtime 能回答：

- 今天原本计划做什么？
- 实际做了什么？
- 哪些计划被推迟或打断？
- 时间实际花在了哪里？
- 这些执行是否推进了待办和长期目标？
- 明天的安排应该如何调整？
